# 实验设计复核与分阶段定量验证协议

本轮复核的对象是实验能否识别原因、能否公平比较、能否外推到原始业务，而不是仅检查 demo 能否运行。上一版已经具备独立任务和 DAG 两套工程、原始记录及守恒检查，但已有的“每配置 2 次、每次 3 秒”主要是机制探索，不能据此确认 0.5%～1% 的业务收益、稳定 p99、最佳线程数或 ARM NUMA 最优策略。

**修订后的目标是每项结论都有对应的受控对照、有效性检查和明确的适用范围。** 不需要穷举所有参数的笛卡尔积；需要先标定容量、再逐个引入机制、最后用未参与调参的混合负载确认。阶段入口仍是 [五阶段验收](README.md)，基础实验见 [阶段 3](03-independent/README.md)，真实图近似见 [阶段 4](04-dag/README.md)。本文件是优先级和实验协议，不把“已设计”“代码支持”“本机实测”“目标机验证”混为同一完成状态；本轮执行事实以仓库验证记录和原始 manifest 为准。

## 1. 复核发现及优先级

|优先级|发现|如果不处理会得出什么错误结论|修订与验收要求|
|---|---|---|---|
|P0|3 秒、2 个 seed 的重复不足；DAG 每轮通常只有 36 个 request|把极值附近的经验 p99 当稳定尾延迟，把某一轮抖动当策略收益|以整轮为重复单位报告配对差值；短实验明确为探索；正式尾延迟另收集足量请求和时间跨度|
|P0|固定 12 arrivals/s 同时把 burst 从 20 增至 400，会使总任务率增大 20 倍|把增加总工作量导致的排队，全部归因于“扇出形态”|分别保留等平均任务率的 burst 对照、固定到达率的需求增长对照|
|P0|直接增加 2% 的 8 倍长尾会使平均服务需求增加 14%|把负载升高导致的拥塞，解释成方差或估计器失效|同均值分布对照与原始参数的增压实验分开；记录有限样本实际预算总和|
|P0|开放环整轮包含启动、过载增长和 drain；总体相关可能由共同时间趋势产生|宣称高相关证明稳态队列模型，或把 drain 中完成算入可持续吞吐|按计划到达选择 cohort，另看队列/未完成数趋势、前后半变化和完成率；持续增长标为 overload|
|P0|“同 seed”不一定等于相同到达、图、预算及 RPC 序列|路由对照实质拿了两批不同难度请求|校验允许变化参数之外的配置与逐条工作量签名；失配不计算配对收益|
|P0|CPU 时间预算模式固定了消耗的线程 CPU 时间|把固定 CPU 预算下的时延改善解释成缓存亲和节省 CPU|机制实验保留 CPU 预算模式；局部性实验改用固定工作量，独立校准并验证内存驻留|
|P1|当前人工 CPU 分区是同一 VM 的逻辑 CPU 子集|将分区收益当成跨 ARM cluster 或 NUMA 结果|本机只验证排队和路由机制；目标机核实 core、SMT、cache、NUMA、允许 CPU 并集|
|P1|真实业务同时给出 QPS、平均时间、CPU 占用和很宽的节点数范围|构造一个远超机器容量的“真实负载”后据此推荐策略|先做 CPU 需求守恒；端点压力、典型负载、容量归一化各自单列|
|P1|只测初始 fork 或完整屏障图|把初始扇出均衡收益推广到普通链、RPC 恢复或任意 DAG|增加多波、深链、RPC 恢复的决策范围对照；任意图尚未实测时保持结论边界|
|P1|work 指标可使用已知合成预算，生产通常没有该信息|让复杂指标享有信息优势，再宣称它必然优于原生 queue|oracle、固定值、偏差估计分层；预测精度和插桩/决策成本一起评估|
|P1|DAG 完成后仍占 admission slot，直到异步日志落盘|日志瓶颈导致拒绝被解释成 executor 算力不足|同时报告 request 实际未完成数、日志模式和拒绝；主性能对照要求没有日志背压证据|
|P2|路由阈值在所有结果中挑最好的一项|汇报的是选择偏差，后续场景收益消失|用探索集调阈值，再用独立 seed/负载测试；预先声明主要对照和最低有用收益|

P0 是计算可信定量差值的前置条件；P1 是将结果用于真实业务决策的前置条件；P2 防止把局部最优误当通用配置。不能用增加总任务样本数代替独立重复和正确对照。

## 2. 首先校验业务参数是否能同时成立

需要澄清的不是“100 ms 是否准确”一个问题，而是它的测量范围：线程 CPU 时间、回调墙钟、含 RPC 等待的算子端到端时间，分别对应不同容量模型。

设每 request 有 N 个算子，算子线程 CPU 需求为 S，join、调度和其他阶段另计，则 executor 的平均需求为：

`D_executor = QPS × E[Σ S_i + join CPU + executor 调度 CPU]`。

若“整体 50%”是以 96 个逻辑 CPU 的 CPU 时间总额为分母，整体约为 48 CPU 秒/秒。executor 只占其中一部分，所以 12 QPS 时平均每请求 executor CPU 预算不应超过约 4 CPU 秒。假设每算子真有平均 100 ms 线程 CPU，那么平均算子数的粗上界约为 40，扣除其他 CPU 消耗后还会更低。这个推算以利用率口径正确为前提；若监控分母、采样窗口或时间定义不同，必须重新计算。

因此：

- 20～400 是范围，不能自动假定均匀分布。均匀取值的均值是 210；12 × 210 × 0.1 = 252 CPU 秒/秒，与上述平均占用明显不相容。
- “初始同时 ready 的数量”“整张图算子数量”“CPU 回调数量”不能互换。RPC 拆段会增加回调数，但不一定增加原始计算预算。
- 2% 的 8 倍尾部加在 100 ms 基础值上，均值是 114 ms；如果业务所说的 100 ms 已经包含尾部，合成分布应下调非尾部中心。
- 若直接模拟 700～800 ms 的绝对尾部，以概率 p、尾部均值 750 ms 表示，且总体均值要求 100 ms，则非尾部均值为 `(100 − p×750)/(1−p)` ms。例如 p=0.02 时约 86.735 ms。概率须来自业务或显式标为假设，不从“个别”推断精确占比。
- 48 个物理核、96 个逻辑 CPU 不是两倍有效计算吞吐。CPU 时间预算能分摊 96 条逻辑执行时间线，不代表固定工作量的吞吐翻倍。

测试机需要采集 N、初始 ready 数、关键路径深度、每 request 总 CPU、每算子 CPU/墙钟、RPC 比例及等待、请求大小与数据复用的联合分布。先看分位数和条件分布，再拟合负载；独立打乱所有参数可能抹掉“大图更慢”“大图更易 RPC”等相关性。没有生产分布时，使用明示假设的受控扫描，不把任一人工分布命名为“生产重放”。

## 3. 公平对照的合同

每组比较先列出以下五项，随后按结果文件核验：

1. **目标问题和主要结果。** 例如“相同需求下集中投递是否增大 task 等待”，主要结果为 planned→finish 均值，submit→start 是机制辅助量；DAG 则以 request 端到端时延和完成率为主。
2. **允许变化的变量。** 例如仅 policy；或者 burst 大小及与之配套的 arrival rate。不能把所有配置差异都自动视为允许。
3. **必须相同的外生工作量。** seed、请求/任务 ID、目标工作预算、RPC 选择与延迟、计划到达时间、图结构；仅当实验问题本身改变其中某项时放行，并记录比较口径。
4. **相同的资源和测量。** 总 CPU 集、线程数、CPU quota、优先级、采样、日志、编译与 Folly 版本、工作循环、数据规模。
5. **失败规则。** 工作量失配、文件缺失、守恒失败、未解释的发生器滞后、拒绝/取消、持续积压、内存/日志瓶颈如何处理。

“同种子”仅是可重复生成的前提，不是合同已通过的证据。调整随机分布调用次序、RPC 分支、工作量模式、不同标准库实现，均可能改变后续序列。路由实验应检查逐 request/节点预算和到达计划；burst 对照通常无法保持每个任务的到达时刻，但应保持任务数、服务预算序列或总预算、总任务率。

改变图形时，保持总节点数与预算序列并不保持关键路径；关键路径变化正是此组实验的处理变量。不能同时宣称它是“纯策略对照”。改变线程数、SMT 或允许 CPU 集时，要区分同资源调度实验与改变容量的资源实验。

对照与处理每个 seed 都执行，独立重复之间换 seed。随机执行顺序，避免“全部 baseline 在前、全部优化在后”。有明显机器状态漂移时，采用同一轮内交错的短块或成对近邻顺序；不要一边加载其他 CPU 实验一边跑主矩阵。机器噪声属于结果的一部分，预先规定异常运行处理规则，不根据收益方向删轮次。

## 4. 容量标定先于负载比例

单个固定配置的标定顺序：

1. 记录 CPU mask、SMT sibling、cache/NUMA、每层 cgroup quota、CPU 频率策略、后台工作，以及本次可用核。
2. 用固定服务分布、固定线程数、无 RPC、K=1 的开放环任务逐步提高 arrival rate；先 30～60 秒试运行，再对边界附近做更长重复。
3. 在测量窗口比较到达率、完成率、未完成工作量变化，以及前后半等待/队列分布。若队列持续增长，或主要完成发生于停流后的 drain，该点不是稳定容量。
4. 记录最高已确认稳定点与最低已确认不稳定点，形成容量区间；有限观察无法证明边界精确值。选择明确位于稳定区的负载，而不是把边界的小数点后几位当真。
5. 为同分布同配置计算 `λ_offered / λ_sustainable`，标注它是经验负载比例。改变服务分布、亲和、线程数或固定工作循环后，必要时重新标定。

测试目标负载可取经验容量的约 25%、50%、75%、90%，另设 105%～120% 的有限 overload 探针。后三种“容量”的含义不同，报告必须区分：

- 固定工作的实际 tasks/s：适合比较有效吞吐和数据局部性。
- 实测线程 CPU 秒/秒：用于 CPU 时间守恒，不等于固定工作的吞吐。
- 以逻辑 CPU 个数作分母的名义需求：只作初筛，不应标成已校准 ρ。

同 NUMA 的三个池若共用一个 mask，不能给每池各计一次完整 NUMA 容量。调度器中的 capacity 参数也应与这种共享关系一致，否则 work/queue 换算的预测时间会失真。阶段 4 先用 home 比较部署，避免将容量估计和动态选池两个机制同时改变。

正式报告将稳定运行、过载探针、有拒绝/取消的有界系统分开。后两类仍有价值，但研究问题分别是积压增长/恢复和过载保护，不能与无损稳态系统只比成功请求时延。

## 5. 阶段 3 的最小充分覆盖

|实验族|固定项|对照变量|能够支持的结论|不能支持的结论|
|---|---|---|---|---|
|容量|资源、线程、服务分布、K=1|逐级任务率|该配置已观测稳定区与过载区|任意图或任意分布容量|
|突发规模|总任务率、服务预算、资源|K=1/20/100/400；arrival rate 反比变化|等平均需求下集中到达影响|固定 12 QPS 下增加任务数没有代价|
|集中位置|每次 burst 的任务和到达时间|整批到一个 RR 池 / 同批分散到多个池|局部集中与全机总需求的区别|DAG 迁移局部性收益|
|到达变异|期望任务率、服务分布|regular / Poisson|到达抖动对等待和指标的影响|任意线上相关突发重放|
|服务异质性|平均预算、任务数、到达|固定 / 均匀 / 稀疏长尾|相同均值下队列个数和工作量差异|增加长尾时总需求保持自然不变|
|时间尺度|名义 CPU 需求比例、分布形状|短任务高频 / 长任务低频|调度和计量成本相对服务量的变化|将毫秒循环直接等同真实 100 ms 算子|
|资源及线程|相同外生工作、允许 CPU 并集|none/numa/cluster × 核附近/逻辑宽度附近/过量线程|绑定和并发槽对等待的作用|CPU 越多或线程越多必然更快|
|指标信息|工作量、策略前提、测量窗口|queue / pending / inflight / oracle-work / 有偏估计|不同信息在相同覆盖样本的预测增益|预测更好必然产生更好路由|
|观测成本|固定迭代数、同任务、资源|none/queue/counters/full，采样周期|整轮 CPU/吞吐/时延的实际增量|热缓存单次读成本等于端到端成本|

测试环境三种绑定始终使用同一份六 cluster CPU 组；none 也限制在这些 CPU 的并集。物理核单线程与 SMT 双线程的比较是另一项资源实验，不能偷偷改变 only-none 的 CPU 数量。

相同理论均值的分布，有限样本预算仍可能不同。可选两种合法分析：一是保留自然随机波动，报告每轮实际总预算并在 run 层配对；二是预生成后将这一轮总预算归一到相同值，直接隔离分布形状。后者是受控合成实验，各任务不再是独立原始分布抽样，取整后还须核验总预算；不可声称它保留未经条件化的 IID 分布。不能同时要求逐任务预算完全相同和服务分布改变。

regular 与 Poisson 在固定时长内的请求数可不同。Poisson 不应在期望数量处截断繁忙 seed。可以报告同期期望压力，或另外定义固定计数的到达实验；二者是不同实验，不能通过默默截断使预算看似完全相等。

预测误差除均值 MAE 外，应看高等待区的漏报率、queue=0 时超阈值等待比例及样本覆盖。相关性在低负载下可能没有方差，在过载趋势下又可能虚高。整轮留出比随机拆 task 更合理，但 2 轮互训仍只是探索；若在同一验证集反复选模型/阈值，必须再设独立测试集。

## 6. 阶段 4：贴近真实业务而不混淆多个机制

### 6.1 三类负载各自命名

- **业务参数压力组：** 固定 12 QPS，显式扫描总节点数、初始 ready 数和 100 ms 平均/700～800 ms 尾部假设。极大图可超载，结论是边界与保护行为。
- **容量归一组：** 保持图形和服务分布，以已标定容量调整 QPS 或工作规模；验证均衡策略随压力的变化，不宣称所有组均是 12 QPS 真实业务。
- **生产分布重放组：** 只有获得实际联合分布或 trace 后才使用此名称。保留图大小、形状、CPU、RPC、数据大小之间的关联。

开发机缩短算子 CPU 预算并保留 12 QPS，可检验 request 重叠和 fork/join；但服务/调度开销比例、睡眠唤醒间隔、cache 驻留和迁移代价均会改变。应补“同名义需求、不同任务时间尺度”实验，避免从 1 ms 合成任务推断 100 ms 算子的百分比收益。

### 6.2 分步路由实验

|顺序|问题|建议主要对照|需要同时报告|
|---|---|---|---|
|4B|单纯绑定有何代价|home 固定；none/numa/cluster × 线程数|request 时延、submit→start、回调 wall/CPU、各池压力和总吞吐|
|4C1|跨池分散是否解决初始集中|home / fanout-initial|同初始 burst、总工作和 request 到达；迁移次数、等待下降、服务变化|
|4C2|后续 fork 还需均衡吗|fanout-initial / fanout-all|后续波宽度、波间关键路径、各波等待|
|4C3|普通链与 RPC 恢复要不要继续均衡|fanout-all / sticky|深链与 RPC 单独引入；普通 successor/RPC continuation 的实际去向|
|4C4|后继优先回 home 还是跟随 parent|borrow / sticky|相同候选范围、阈值；借出、回迁、再次迁移和 request 时延|
|4C5|更复杂指标是否值得|同策略 queue / pending / work；相同单位收益阈值|原始负载、预测误差、决策成本、请求收益；oracle 与有偏估计分别列出|
|4D|是否只对某种图有效|相同节点/预算的前重、均匀、后重、深链|关键路径变化、初始/中途 fork 的差异；不要仅看全图累计等待|
|4E|压力与不均匀工作是否破坏收益|分别加入长尾、RPC、到达抖动、稀疏大图|均值需求是否匹配、实际并发请求数、拒绝/取消；最后用混合场景确认|
|4F|局部性成本是否抵消等待收益|固定工作、真实内存位置；留原池/同 NUMA/跨 NUMA|路径等待、服务 CPU/wall、跨域访问、数据大小、路由读取与迁移开销|

4C3 不应只比较 home 与 sticky：这会同时引入初始分散和后续每次决策，无法回答普通 successor 是否需要再次均衡。4C4 的 join parent 约定必须相同，否则混入多输入数据的亲和决策差异。

先在固定图、无尾部、无 RPC 下完成策略比较，再逐个增加变量。最后保留一组不参与调参的“多请求重叠 + 初始扇出 + 中间 fork + 长尾 + RPC”场景，检验组合后收益是否仍然成立；组合组本身不用于单机制归因。

### 6.3 尚不能由当前本机数据确认的局部性问题

现有原型能够记录 source/chosen 标签、迁移次数和配置迁移惩罚，但**惩罚参数是决策模型，不会自动制造真实迁移成本**。同 NUMA 标签也不是数据一定在本地的证据。以下条件需要目标机工作和/或后续扩展，不能以现有短轮次替代：

1. 核实 cluster 是否为共享 cache 域。已有本机记录是 KVM、单 NUMA、4 逻辑 CPU、报告 2 core × SMT2，全部共享 LLC。`0,1;2,3` 是人工分组，不是两颗 ARM cluster。
2. 固定工作量并测算子实际服务成本。CPU 时间预算模式会在 cache 访问变慢时少执行迭代，从而隐藏工作损失。
3. 控制数据 first-touch、页驻留与 CPU 位置，记录 NUMA balancing、页迁移、THP 等环境因素。当前主线程初始化的只读共享数据不等同于 home pool 本地页，更不等同于真实中间结果。
4. 分别测试单 pool、限制在偏好组 NUMA 的多个 pool、允许跨 NUMA 的多个 pool。本轮路由器补充 `CandidateScope::All/PreferredNuma`：Borrow 以 home 为偏好，Sticky/Fanout 有 parent 时以实际 parent 为偏好；LeastLoad 也遵守范围。未知标签在 PreferredNuma 下拒绝。它是严格的标签候选过滤，不是内存本地化；worker mask 和物理 node 仍须核实。Borrow 若收到外部跨域 parent，仍允许回 home，因此不能把此接口解释成禁止一切 source 跨域。仅把跨域惩罚设成大数是阈值实验，不能代替候选域隔离。
5. 数据规模至少覆盖小于私有 cache、可共享 cache、明显超过共享 cache；同时考虑 `同时存活 request × 每 request 数据量`，防止把内存容量/带宽变化当调度差异。
6. 当前只读请求数据不模拟可写中间结果、cache line 争用、数据复制、部分扇入、多消费者共享和任意跨波依赖。这些结论必须由对应工作负载验证。

跨池放置是把新就绪任务投到另一个池，不是搬运已经排队或正在运行的 closure。其净收益应在相同外生工作下直接测量；不能简单将“迁移任务均值 − 留原池任务均值”解释为迁移成本，因为策略恰好会把繁忙或困难任务选择性迁移。为了估计服务层跨域成本，应在低负载、固定放置的独立试验中比较，之后再看繁忙系统里的总收益。

## 7. 定量分析的统计协议

### 7.1 窗口与状态

正式实验至少分清启动/预热、测量投递、排空三个区间。测量 cohort 按计划到达时间选择，入选的慢请求允许在窗口后完成；不能只挑窗口内完成的请求。报告全部状态：offered、accepted、completed、rejected、censored、failed，并报告超出窗口的完成及 drain。

发生器迟到单列 planned→submit；用户关注的体验至少保留 planned→finish。按完成秒的均值/p99可作观测面板，按计划到达秒的趋势更适合检查同一外生负载是否随时间恶化。整体 p99 从原始入选样本重算，不能平均每秒 p99。

每轮至少检查前/后半到达率、完成率、未完成数/queue、时延与发生器 lag。趋势诊断是警报，不是稳定性的数学证明：在突发系统中，单个线性斜率可能被周期波动或采样混叠误导。至少观察多个突发周期；保留原始时间序列，必要时更改采样周期做稳健性检查。

### 7.2 重复和配对

以 seed/完整运行作为主要独立重复单位。对每次重复计算处理相对 baseline 的绝对差值、相对差值，并保留逐次结果。均值差的 bootstrap 必须重采样配对的 run，而不是把几十万个相关 task 当几十万独立实验。5～8 次可用于本机大效应复验；正式确认细小收益通常需要更多重复，数量由 pilot 波动和最低有用收益决定。

置信区间不包含 0 也不能自动证明外推成立。需要同时看差值大小、完成率、资源代价、运行状态、配对合同和结论范围。区间跨 0 意味着当前信息不足以确认方向，不等于两策略等效；要宣称“开销不超过 1%”，应预先设定可接受边界并有足够精度。

如果一个家族探索几十个候选，只报告最大改善会有选择偏差。预先指定主要对照；探索性比较全部保留，选定方案后用独立 seed/负载确认。不能反复增加运行次数直至显著而不说明停止规则。

### 7.3 p99 的样本边界

12 QPS × 3 秒约 36 请求，经验 p99 通常就是该轮最大值；8 秒约 96 请求也只有约 1 个理论上位于 99 分位以上的观测。它们可以报告为描述性数据，不能声称稳定尾延迟已被验证。

一个实用采样检查是同时报告 N、`0.01×N` 的期望尾部数量、实际持续时间及重复数。N=10,000 时期望只有约 100 个 99 分位以上样本；12 QPS 收集 10,000 请求约需 833 秒的有效测量时间，尚未计预热、拒绝或相关性。10,000 不是保证准确的万能阈值；尾部分布越陡/越重、时间相关越强，需要的样本和时间越多。

合并多轮原始请求得到的是混合分布 p99，不能代替逐轮 p99 的稳定性分析，更不能对 p99 做“平均各秒分位数”。需要给分位数不确定性时，以独立 run 或足够长的时间块重采样，保留 request/burst 内相关性；不要使用 task 的 IID bootstrap 生成虚窄区间。

### 7.4 因果与路径解释

队列深度与时延的相关性用于筛选观测指标。受控策略/部署/突发对照才用于判断改变某机制后的效果。高队列和高时延可能共同来自总需求、长任务、时间趋势或选池行为；单个 Pearson/Spearman 不能消除这些因素。

DAG 请求时延沿完成路径分解。全图所有分支等待之和可衡量浪费，但不是 request 端到端等待。回调 wall−CPU 可能包含抢占、阻塞及计时开销；submit→start 包含用户队列、通知与调度，不可直接称 Linux runq。需要内核归因时做单独追踪，并对照追踪扰动。

## 8. 本机小矩阵的用途与停止条件

为确认修订后的生成、配对、cohort 与统计链路，建议采用以下有明确问题的小矩阵，而不是再追加很多 3 秒探索配置：

|组|配置|重复与窗口|用途|
|---|---|---|---|
|独立任务 burst|2 池各 2 线程；相同 CPU 分区；每任务 2000 μs、±50% 随机、无额外尾部；1200 task/s；K=1/20/100，对应1200/60/12 arrivals/s|建议 6 seeds × 8 s；planned 1～7 s 为示例测量窗口|相同需求下 burst 的均值/等待变化；有限样本预算配对；K=100 同时保留 12 批/s 的外部节奏|
|DAG 请求重叠|2 池各 16 线程；12 QPS；40/10/10 三波；4000 μs/算子、100 μs/join；queue；home/borrow/fanout-initial 或预先选定另一策略|建议 6 seeds × 8 s；scheduled 1～7 s 为示例测量窗口|复验大效应是否跨重复成立，检验请求级配对与状态；不作为正式 p99 样本|

这两个名义 CPU 需求分别约为 2.4 和 2.884 CPU 秒/秒；相对 4 个逻辑 CPU 的比例不是已标定有效利用率。运行前先做 pilot，若发生器明显跟不上、后半持续增长、日志背压或严重干扰，先修复/降低负载再完整执行。最终参数和结果以实际配置及 manifest 为准，不将本表的建议值冒充已执行事实。

一秒预热只是开发验证的窗口示例，不能替代目标机的热稳定确认。上述 DAG 每轮测量约 72 request，短窗口 p99 必须保留“小样本，仅描述”标签。增加六次重复主要改善均值差方向的可信度，并没有自动解决单轮 p99 样本不足。

## 9. 测试环境的逐步执行与决策门槛

1. **阶段 1：业务自洽。** 明确 CPU/墙钟口径和平均图工作量，给出一组典型值及可解释的范围。若不自洽，不给“真实稳态”配置贴标签，继续受控扫描。
2. **阶段 2：指标语义和成本。** 固定 Folly 版本验证 queue 语义；先读原生 queue，再比较必要的附加统计。轻载/繁忙、线程数、跨域读写成本分开；不要先验否定 queue。
3. **阶段 3：基础关系。** 完成功能、容量、等需求 burst、同均值异质性、线程/亲和、计量成本。若 queue 已足以区分关键拥塞且补充指标增益不足，保持简单基线；这不是宣布所有业务都不需要其他信号。
4. **阶段 4：图与策略。** 先完成无局部性 CPU 模型的部署和策略对照，再做后续 fork/链/RPC 范围，最后单独验证局部性和混合场景。没有 4F 的真实证据，允许得出“分散减少等待”，不能得出“某 NUMA 策略生产最优”。
5. **阶段 5：实现归属。** 同工作量、同策略对照业务侧与 Folly 扩展，验证语义和生命周期一致。把代码放入库不天然带来更好调度；必须以复用边界、维护成本和接入约束做决策。

每步保留设计版本、有效命令、二进制/源码标识、机器信息、原始记录、每轮状态、配对合同及未满足门槛。通过哪一步就只宣称哪一步的结论。现有工程适合验证用户态排队、初始集中和路由策略的受控关系；生产 NUMA/数据亲和、任意图、真实 RPC 与动态业务分布仍要由相应环境和负载补齐。
