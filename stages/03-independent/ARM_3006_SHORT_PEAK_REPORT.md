## 1. 本轮究竟在运行什么

|项目|配置与统计口径|
|---|---|
|资源|6个原生Folly池，每池128worker，绑定不重叠的16逻辑CPU；共96CPU，两NUMA分别3池|
|到达|单生产者开放环12request/s，home轮询；不同home错开83.333ms，同home周期500ms|
|initial|80项独立CPU任务，约1ms内计划投递，每项标称平均1.020ms CPU|
|steady|另外80项独立CPU任务，从1ms起分散于500ms窗口，每项标称平均48.980ms CPU|
|随机与预算|±50%预算波动，分别对两阶段整轮归一化；每请求名义总计4 CPU秒，12QPS对应48 CPU秒/秒，即96CPU的50%|
|CPU预算构成|initial只占每请求CPU预算2.04%，steady占97.96%；任务数量各占50%|
|调度|本次全部任务留原home；尚未执行分流。计划候选source_only在提交前home的N/C>0.8时选择其他池中严格更轻者，无合格目标留home|
|观测|CPU旁路事件积分1ms，附100ms累计计数；CPU不参与路由或自动控制发压|
|样本|60秒生成，排除前10秒；600个完整request、96000个任务，initial与steady各48000项，保留后续释放及排空完成|

这是独立任务的CPU需求形状模型。steady不是DAG依赖完成才释放，request最后完成还受固定后续投递窗口影响；本轮没有测出生产图请求收益。真实5–20ms仍是粗略观察，90%不是业务已确认的占用阈值。

S是应用提交入口到计算结束，W是该入口到回调开始，X是回调墙钟时长，L从本项计划释放到结束，D是实际提交迟到。逐项`S=W+X`、`L=D+S`，p99不能相加。N为已预留/接纳而未完成的任务数，Q为Folly近似任务队列，C=16是逻辑CPU容量刻度，均不是Linux runq或CPU百分比。

## 3. 为什么软件仍判失败

|同trace高占用阈值|首段宽度median/p90/max|碎峰比例|
|---|---|---:|
|80%，敏感性|9/10/13ms|7.333%（约44/600）|
|90%，冻结验收|8/10/12ms|13.833%（约83/600）|
|95%，敏感性|7/9/12ms|13.000%（78/600）|

碎峰的代码定义是：取首个在请求开始5ms内出现的连续高位段；前30ms中，**其他高位段累计超过2ms**即记一波碎峰。若高位区间为`[0,2]ms`和`[3,9]ms`，首段只有2ms，其他高位6ms，判为碎峰，但整个高位事件的包络仅9ms。

仅凭原3006终端汇总，13.833%既可能来自一个短事件内部的阈值穿越，也可能来自较晚的第二个峰；后续分段复核已区分，见第5节。**我此前将碎峰比例≤10%设为硬门槛，是额外的合成形态假设，不是用户确认的业务要求。不能仅凭这一项认定负载设计仍有问题；也不能看到结果后直接把10%调成15%、换80%口径或改称原合同通过。**

实际初始80项投递跨度平均1.707ms、p99=8.880ms，计划跨度0.988ms；投递端的时间展开也应随碎峰一起检查。它可能影响形态，但本日志不能证明碎峰由投递迟到造成。后续比较必须保留L和D，不能只用S掩盖发生器迟到。

## 4. 任务时延及N/Q指标能说明什么

单位ms。均为本次home，没有策略A/B差值。

|阶段|S均值|S p99|W均值|W p99|X均值|L p99|
|---|---:|---:|---:|---:|---:|---:|
|全部|26.789|72.796|1.635|7.834|25.154|72.922|
|initial|4.353|9.928|3.154|8.248|1.199|10.500|
|steady|49.225|73.310|0.116|5.815|49.109|73.425|

initial的平均耗时主要是等待，存在待检验的调度改善空间；steady平均耗时主要是自身CPU工作。steady预算范围约24.5–73.5ms，所以全体p99接近73ms并不意外。即使initial明显变快，全体p99也可能不明显变化，不能以“全体p99必须大幅下降”作为策略成功的唯一判据，也不能忽略steady回归。

本轮更不能混合两阶段判断指标：

- 全体`N/C<0.5`桶25798项，其中25344项是steady，占98.24%；该桶S p99=73.171ms，主要反映长任务自身成本。
- 全体`N/C≥4`桶11380项，其中10829项是initial，占95.16%；其任务构成已与低N桶完全不同。
- 因此“低N桶p99很高，高N桶反而低一些”不能直接解释为N失效，也不是简单坐标轴问题。这里有明确的任务类别混合；应分阶段看等待和完成时延。

initial内的原始分桶如下：

|N/C区间|任务数|S均值|S p99|W均值|
|---|---:|---:|---:|---:|
|[0,0.5)|454|1.041|1.535|0.017|
|[0.5,0.8)|3691|1.048|1.548|0.020|
|[0.8,1)|2978|1.118|2.128|0.064|
|[1,2)|10630|2.404|8.416|1.182|
|[2,4)|19418|4.916|9.413|3.640|
|[4,+∞)|10829|7.410|10.803|6.268|

initial的N与等待/完成时延呈清楚的分桶上升趋势。Q也有类似趋势：`Q/C<0.5`时S p99=2.688ms、W均值0.343ms；`Q/C≥4`时为11.337ms、7.392ms。两种桶覆盖的任务不同，不能只比端点p99宣布N优于Q；也不能用六个聚合点代替逐任务相关性分析。N低于0.5的initial桶仅454项，尾部标记LOW_TAIL，应避免过度解释。

这份日志没有active/inflight分桶，也没有active驱动路由数据，因此不能回答active能否在本负载替代N。N对约1ms和49ms任务等权的局限仍然存在；当前不同时修改指标和策略，以免失去归因。

## 5. 已完成的离线复核与继续对照的依据

用户在同一测试机读取原trace并返回[完整终端摘要](../../results/stage3-arm-3006/inspection-terminal.txt)。600/600请求可用，83个原碎峰与manifest、summary、原逐波CSV全部一致。这是原数据的离线细分，没有新增压力轮次。

|量|全部600波|原碎峰83波|
|---|---:|---:|
|存在≥90%高位的波|598|83|
|高位包络median / p90 / p99 / max|9 / 10 / 12 / 13ms|9 / 11 / 13 / 13ms|
|最后高位结束时刻max，首提交后|13ms|13ms|
|20–30ms高位累计量max|0ms|0ms|
|实际initial投递跨度median / p99|0.986 / 8.880ms|4.032 / 10.698ms|

全部波包含513个单段、85个分段和2个未达到90%的波；原碎峰中82个分段、1个单段。46个分段波的所有段间低谷均不超过1ms，其他分段的最大间隔可达5ms。因此不能把全部碎峰解释为1ms低谷，但全部高位都局限在13ms内，且没有30ms窗口截断。

单段也能被原规则标为碎峰：request 247的高位仅`[6,13]ms`，由于起点超过5ms，找不到符合条件的起始段，于是这7ms全计入extra。原碎峰字段实际上还包含起峰较晚的情况，不等于存在长峰。request 567虽分成`[0,1]、[3,4]、[7,13]ms`，整个高位包络也只有13ms。

逐波后段（30ms起至本波分析窗口结束）的高位时间比例max=0、最长高位段max=0。这不代表后段CPU空闲：3006的占用约50%。也不排除低于90%的波动或小于1ms的尖峰。碎峰波的投递跨度较大，与投递展开有关联，原因尚不能仅凭这些摘要确定；下一轮继续记录D和L，不修改投递实现。

**决定：保留原strict=failed，通过明确记录的事后复核，继续这组短峰形态下的描述性策略对照。** 接受的是短包络与恢复背景这一研究目的，不是把原“碎峰≤10%”门槛改成通过，也不是验证了真实业务的精确波形。已有完整home不用丢弃或重跑。

## 6. 下一步仅补source_only一次

保持原计划、C++二进制、每池128线程、cluster亲和、12QPS、全部CPU预算和采集方式不变。source_only仍对initial/steady每项提交检查home的`N/C>0.8`，满足时选择其他池中严格更轻者，允许跨NUMA，没有目标0.5接纳上限。没有更轻者仍留home。阈值是本轮固定候选，不是已证明的生产最优值。

在测试仓库执行；不需要重编译，也不要重新生成plan：

```bash
git pull --ff-only origin experiment/stage3-load-balance-20261115
python3 experiments/independent/scripts/request_wave.py run \
  --plan results/short-peak-arm/plan.json \
  --binary build-independent/independent_load \
  --reviewed-short-peak-inspection results/short-peak-arm/short-peak-inspection/inspection.json
```

新参数只支持已经存在且身份匹配的home及其离线证据；不能用于缺失覆盖、长峰、其他失败原因或通用跳过验收。正常打印`SKIP home`，随后只新执行一次source_only。原`home_waveform_gate.passed=false`及严格失败原因继续保留，新增`home_waveform_review.status=accepted_posthoc`单独记录复核依据和证据指纹。未给此参数时仍执行原严格门禁。

保留已经生成的`inspection.json`，无需再次执行离线检查。复核记录绑定它的内容指纹；成功续跑后顶层manifest会变化，重新生成inspection会产生另一份证据。再次运行同一续跑命令会复用已完成策略，不重复发压；不要删除结果目录来绕过身份检查。

脚本自动重做派生分析。完成后打印下列两份摘要即可，无需上传原始文件：

```bash
cat results/short-peak-arm/analysis/report.txt
cat results/short-peak-arm/cpu-curves/report.txt
```

本次验收只检查四件事：

1. A/B的工作量、资源、二进制及观测口径一致；任务全部完成，没有靠丢弃或发生器迟到伪造收益。
2. initial的W、S、L均值/p99及其绝对毫秒差；同时列D，评估短峰下可改善的等待量。
3. steady和全部任务的S、L均值/p99是否退化。若initial收益伴随steady损失，明确列出代价，不仅展示有利阶段。全体p99可能仍受约49ms长任务主导，不能用它单独否定或肯定策略。
4. 分流比例、各池及并集CPU占用、峰宽与背景变化；CPU仍不作为路由输入，也不要求分流后继续满足home的波形。

两策略各一次，只给本轮观察差值，不声称显著性、全局最优阈值或生产收益。对照完成后先输出结论，不默认增加guarded、active、none亲和、线程数或阈值矩阵。
