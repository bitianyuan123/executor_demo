# 五阶段工程复核与验收顺序

本次重新审查的结论是：旧版工程完成了真实Folly和多池DAG机制验证，但**不足以作为五阶段的独立交付**。将所有问题塞进一个DAG入口，会让队列负载、请求自身扇出、路由选择和RPC互相影响，也会让使用者必须先接受库扩展才能验证基础问题。保留同一仓库有利于版本和证据对应，运行入口、变量和结论则必须分开。

## 修正清单

| 原交付缺口 | 本次修正 | 验收证据 |
|---|---|---|
| 真实业务背景散落在通用模型中 | 阶段1独立报告，已知/假设/未知分开 | 口径表、容量边界、目标机取证表 |
| 经典LifoSem handoff的例子容易被当成默认队列行为 | 阶段2分别解释默认Throttled与经典LifoSem；区分队列计数准确性和整体负载覆盖率 | 固定源码调用链、指标成本与选择表 |
| 原native queue指标被过早升级为work路由 | 阶段3先以queue作原版Folly低成本基线，再比较新增计数的增量价值 | 独立任务数据、分桶与服务量分层 |
| 简单排队问题也依赖DAG和AffinityExecutor | 新建完全独立的任务工程，只调用原版CPU池 | standalone构建、独立测试 |
| DAG仅独立链加最终join | 新增多波fork/join、可变宽度/深度、二次fork策略位置 | 显式依赖CSV、顺序/次数自动化验证 |
| 阶段4依赖阶段5的实验库 | 业务侧路由器可独立构建，库后端单独启用 | 原版安装头文件下的业务构建、后端契约对照 |
| 把已有数据当作所有问题的证据 | 保留旧实验为历史数据；新阶段结果分别归档 | 新VALIDATION和每阶段RESULTS |

## 顺序与停止条件

“停止条件”是人工验证时的判断门槛，不是本次工程停止开发的理由。

1. **业务报告**：确认100ms是线程CPU还是墙钟；20～400是总节点数还是初始宽度；提供真实DAG宽度/关键路径、每池线程数与CPU利用率分母。无法确认时保留分支假设，不给生产容量结论。
2. **Folly报告**：确认业务实际版本、队列、唤醒间隔，明确native queue、callback pending/inflight、内核runq各自口径。在目标机测读取和维护成本，默认先保留queue。
3. **独立任务实验**：固定任务服务分布，在开发机跑功能和小矩阵；目标机再做6池、三绑定、线程数和负载扫描。若发生器落后、拒绝或持续增长的积压明显，报告过载，不把排空后的样本当稳态。
4. **DAG实验**：先在home策略重建局部burst，再比较借出/跟随/回迁、初始fork/所有fork、RPC和长尾。相同总工作量下改变图形，分别看关键路径、可并行宽度与总CPU。真实局部性结论需额外硬件证据。
5. **归属决策**：业务语义留业务层；只有可复用分组能力、策略接口与收益稳定后才选择库级复用。同算法两种打包位置的功能对照不代表有性能差异。

每一步的输出属于本阶段：阶段3的任务时延不能叫请求DAG时延；阶段4的原始节点等待总和不能叫请求关键路径；阶段2的批均值读取成本p99不能叫业务p99；内核多个线程同时等待的总和不能直接加到请求耗时上。

## 数据与兼容性

旧 `results/` 报告绑定旧版单次交付；新增结果分别写入各阶段 `RESULTS.md`、`results/staged/` 和本目录 `VALIDATION.md`。旧脚本仍用于DAG，新增阶段3脚本只解析独立任务schema。根构建只是聚合入口，各工程均可单独配置、编译、测试，不必先完成下一阶段。
