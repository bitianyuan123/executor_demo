# Prompt 05：按证据做一次有界迭代或结束调优

将下面正文复制给真实应用环境中的agent；没有明确改进假设时应结束，而不是继续扩展矩阵。

---

你在离线真实应用环境中决定是否继续调优。先定位交接包，读取相对于本文件的`../GUIDE.md`、`../EVIDENCE.md`、`../WORKSHEET.md`，再读`tuning-work/STATE.md`和`tuning-work/outputs/01-discover/`至`04-validate/`。当前产物放到`tuning-work/outputs/05-iterate/`；若已有一次迭代，使用子目录`iteration-02/`等保留历史，不能覆盖失败轮。没有此前结果时先做缺失阶段，不自行找更多参数。不要联网安装、clone或向其他环境索取隐含先验。

目标是形成可解释、可回滚、适合本应用的选择，不是找出数学意义上的最优阈值。真实请求接收到最终响应的p99仍为主指标；任务p99、Q/C、N/C及CPU曲线用于解释。CPU不进入实时路由。

先对阶段04作一个决定：

- 已满足约定目标且没有未解决退化：结束调优，保留当前方案和适用边界，不因还能探索而继续。
- 正确性、计数、计时、样本完整性或对照公平性有问题：先修复这一问题；暂不搜索阈值。
- 结果不充分：指出缺少哪项证据，优先延长同配置观察或补一个针对性测量；不自动三次重复。
- 有明确瓶颈和可验证假设：只选择下面一个方向做有界迭代。

允许的方向及判断依据：

1. **源阈值邻点。** 当已有N/C变化、迁移时机和目标余量证据支持“分流偏晚/偏早”，可在0.8起点附近最多选择两个邻点，通常先选一个方向，例如0.6或1.0；具体范围服从GUIDE和现场已确认方案。用户明确固定阈值时不得擅自调整。不要把0.8、0.6、1.0解释为CPU利用率，保持候选范围、线程数与负载不变。
2. **目标接纳条件。** 默认没有目标绝对门槛，但始终要求目标严格更轻。只有迁入后的竞争、原有请求退化或过度迁移证据出现，才独立试较宽的目标门槛0.8。历史0.5在合成demo中曾限制收益，不是默认推荐值；用户另有明确限制时优先遵守。明确门槛是提交前快照约束还是并发预留后的硬约束；既有保护不能为得到更好p99而越权取消。更改目标条件时不同时更改源阈值。
3. **候选池或回归方式。** 同NUMA可用池不足且跨NUMA代价已有证据时，才考虑扩大候选；任务变快但请求未改善且关键路径显示后续就绪拥塞时，才考虑扩大首扇出以外的分流。先保持request home不变。沿迁入池执行后续片段、每次回home重新决定、所有就绪片段都可迁移是不同策略，不能一次混改。它们均不由当前独立任务demo证明。
4. **线程数或affinity。** 若证据指向过多可运行线程、局部CPU瓶颈或缓存/内存局部性，可在固定路由参数下只比较一个worker邻点或一种affinity变化。保持CPU总集合和输入相同；不同时把cluster改NUMA、减少worker、改阈值。重叠CPU组后必须重新审视C定义，不能继续套用独立池N/C。
5. **指标修正。** N被同步阻塞、不同CPU成本片段或不同资源容量明显污染时，优先修正计数边界/任务分类/容量解释，再考虑基于可获取历史CPU时间的工作量估计。估计不得读取未来真实耗时。更复杂指标必须说明采集开销、误差及新增收益；没有必要时保留简单N/C，不为追求更高相关系数而改变输入维持指标恒定。

执行纪律：

- 先写清一个假设、预期现象、反证条件、唯一改变的因素。阶段04默认A/B各一次；首轮累计最多4个性能配置，亲和性、线程数、路由和阈值共用预算。每次至多一个参数的两个邻点，优先只测一个；不做全因子矩阵，不因一轮较好就继续无限邻点搜索。达到验收即停，另一负载场景只有关系到上线条件时才单独设计A/B。
- 复用阶段02的正确性/停止/回滚标准，不临时降低验收门槛；新增方向超出原授权时仍可完成设计与代码验证，生产执行依实际授权。旧授权持续有效，不重复询问。
- 参数与负载固定、原始结果完整保存、请求主指标及CPU口径不变。12QPS时预热后每配置先观察3–5分钟，报告实际请求数及尾部样本；复用可比的更长现有窗口，只有接近验收线或证据不足时才延长。当前对照若受环境/版本漂移已失效，说明为什么需要新的最小对照，不机械补三轮。
- 候选未改善或退化就记录并恢复已验证配置；若现场已触发停止条件，立即按runbook回滚。探索预算到达后输出“当前最好已观测方案”或“尚无可接受收益”，不要宣称全局最优。

请输出：

- `hypothesis.md`：结束理由或唯一迭代假设、所选方向、参数邻点、固定因素和执行范围。
- `results.md`与必要的`raw/`：原始结果、是否支持假设、请求/任务/CPU的关系，以及失败/不充分/不可比情况。
- `final-recommendation.md`：最终建议配置、适用负载与资源、使用方式、观测和回滚条件，明确哪些结论实测、哪些仍是假设。
- `next-trigger.md`：只有出现什么负载/拓扑/阻塞/请求类型变化才重开调优，不留下无边界的“继续优化”任务。
- 更新`STATE.md`：当前真实部署配置、已回滚项、已完成与未完成事项、最终证据路径。

最后用可独立阅读的短报告解释选择：先定义现场负载、N/Q/C、home及策略，再列请求p99/均值、错误与CPU结果。每个阈值标注来源是用户固定、初始假设还是实测后选取；不要只报“收益百分比”或“推荐0.8”。
