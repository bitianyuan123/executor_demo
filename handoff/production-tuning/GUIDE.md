# 真实应用调优参考：先确认资源与任务，再做一个对照

适用对象是多线程 Folly CPU executor、请求初始高扇出、后续有图依赖和 RPC 的应用。本文件可离线使用；实验事实见 [EVIDENCE](EVIDENCE.md)，现场填写 [WORKSHEET](WORKSHEET.md)。任何生产配置都以现场代码、运行证据和已有授权为准。

## 1. 给现场的初始判断

**优先验证 N/C，不直接指定最终阈值；亲和性从当前实现出发，不预设 cluster 最优。** 现有证据说明：线程数远多于 CPU 时，任务离开 Folly 队列后仍可能长时间竞争 CPU，只看 Q 会漏掉这部分；N能覆盖未完成回调。已测纯CPU场景中，按N/C向更轻池分流显著降低了任务时延，但真实请求收益尚未验证。

第一轮只解决一个问题。若当前 cluster 绑定导致某池持续拥塞、同 NUMA 其他池有余量，优先试有限分流；若没有证据说明 cluster 绑定有价值，先比较现状与一种更宽亲和范围即可。若外部 RPC、全机容量或串行关键路径已是主瓶颈，不应继续搜索调度阈值。

|固定的合同|可以按证据改变的参数|
|---|---|
|授权CPU/配额/环境；请求正确性、取消、超时、上下文语义；任务与请求时延定义；原始数据保留；验收与回滚边界|亲和范围、worker数、源阈值、目标cap、候选范围、哪些新就绪任务参与选池|

每轮只改右列一个主要因素。候选可由 agent 设计，但不能把试验过程变为“不断试直到得到正收益”。负结果和不需要改动也是合格结论。

## 2. 先画现场资源与任务图

探索至少回答以下事实，每项给出代码文件/符号、运行输出或配置来源：

1. **入口到响应。** IO接入、worker构图、executor提交、RPC发起/挂起/恢复、DAG后继释放、请求完成分别在哪里；是否有内联执行或绕开包装层的提交路径；谁维护request home。
2. **任务是什么。** 100ms/800ms是CPU时间、回调墙钟、RPC等待还是请求时延？同步等待是否占住worker，是否存在同池future等待、线程局部资源、EventBase绑定、顺序保证或优先级？没有答案时不能直接宣称N就是CPU需求。
3. **池映射到哪些资源。** 实际worker数与动态扩缩容；每worker有效CPU mask；NUMA/cluster/SMT关系；进程与祖先cgroup的cpuset和CPU限额；其他线程/进程是否竞争同域。分别列池mask、重叠关系及实际容量假设。
4. **真实输入。** QPS与请求类型，初始fanout数量/投递跨度，后续就绪的时序，长尾/阻塞比例；平均CPU的分母是全机还是executor CPU并集。不要把原始口述12QPS/50%当成现场已经核实的固定值。

读现有日志、监控和代码优先。必要的细粒度任务计时可先低比例采样，不要求给每个算子增加昂贵的系统调用。缺少联网依赖时复用本地工具；未拿到的事实标“未知”，不要猜测拓扑连续编号或Folly版本。

## 3. 亲和性与容量C如何处理

|布局|CPU约束|调优含义|
|---|---|---|
|cluster|一个池限制在一个实际cluster组内|局部性可能更好，但限制突发可用CPU；最适合检验向其他不重叠域借用计算资源|
|NUMA|同NUMA的多个池可在节点允许CPU内运行|内核可在节点内分配CPU，但各池资源重叠；同节点换池不等于新增CPU容量|
|none|worker不再加更窄的池级绑定，仍限制在**已授权的CPU并集**|内核有更广调度空间；不是放开到整台机器，也不表示数据页自动跨NUMA迁移|

先保留当前线程数、内存策略、CPU并集和工作量，比较现状与一种候选；仅在结果仍不能决定时，再试剩下的一种。不要求三种都跑。当前none已足够好且没有明显局部积压时，不必为应用路由强行改cluster。绑定只能限制线程位置；数据页first-touch、页分布、共享状态和NUMA内存策略需要另行核实。

**C是归一化刻度，不是线程数，更不是CPU利用率。** 六组不重叠且每组16逻辑CPU时，可以先用C=16，记录SMT及任务类型的局限。存在配额、异构核心、外部竞争时，逻辑CPU数不再等于可独享服务能力，不能声称阈值跨机器等效。

三个池都允许在同一48CPU节点运行时，不可把每池C=48当成三份独立容量；六池共享96CPU也不能按总576核推理。两种可行口径是：以共享CPU域汇总N并归一，或给池明确定义容量份额/权重，同时观测域总负载。等分份额只是模型假设，不代表专属CPU。**没有明确资源重叠和C之前，不启用照搬0.8的跨池判断。** 同域内池级积压仍可反映worker/队列不均，但不能解释为借到了另一份CPU。

识别cgroup版本：v2看有效cpuset与`cpu.max`，v1看cpuset与CFS quota/period；还要考虑祖先限额与其他共享进程。CPU带宽配额限制总CPU时间，并不保证给每个池分配固定独占核。容量定义在一次A/B内固定，变化后旧阈值不能无解释复用。

## 4. N的采集位置、成本与正确性

优先在业务统一executor提交适配层增加每池计数，而不是先改Folly库。最低实现需要路由读计数、add前预留、任务生命周期结束时释放；Q可继续采样作诊断。每项通常增加一对原子读改写、选池时少量原子读取，不扫描几百worker，也不在热路径访问`/proc`。精确成本必须在现场测；共享缓存行的竞争可能高于单次指令成本。

一个N只跟踪**本次已提交的CPU回调片段**。异步RPC发起片段退出即释放，网络等待阶段不占这个N；响应到来形成新的就绪片段再计入。同步阻塞仍会占worker并留在N里，此时N是未完成回调数而非纯CPU需求。先识别、分离或明确限制后再使用，不把整条请求或所有未就绪DAG节点计进N。

建议状态流：

```text
新CPU片段就绪 → 判断可迁移性/已有准入保护 → 读home和必要候选计数
             → 决定目标 → 为目标建立唯一预留 → 调用该池add
                 ├─ add失败：释放预留，保留原有失败处理
                 └─ 已接纳：预留随任务所有权转移
                           ├─ 回调执行、异常退出：结束清理，释放一次
                           └─ 未执行即取消/丢弃/关闭：销毁或取消路径释放一次
```

提交失败、取消先于执行、取消与完成竞争、超时但任务仍运行、对象销毁、池关闭、异常、内联执行和后继同步提交必须逐一核对。**超时通知不是任务已经停止**，不能提前释放仍在执行片段的N。使用唯一所有权/RAII或等价状态机保证恰好一次释放，不能靠两处无条件减一。结束时间戳与N清理时刻分别记录或说明。

近似读数可用relaxed原子；这不允许普通变量并发读写。不能用未定义行为换取“少量误差”。可考虑缓存行隔离，先测量再增加分片计数；分片会影响瞬时读数和路由反馈，不是无代价优化。

多生产者同时看到最轻目标会争抢：必须在add之前立即反映预留；同分打散可采用轮转/哈希等低成本方法。它仍不是原子“全局最轻并接纳”。若目标cap被定义成**硬的转入准入条件**，需要CAS或等价受控预留、明确判断包含当前项与否、有限重试及回退；后续home任务仍可到来，所以硬转入门槛也不是池的永恒负载上限。现有业务的总积压、内存和下游并发保护必须保持。

## 5. 初始策略与有限梯度

下面是**现场可采纳的初始假说**，不是3005已经验证的生产方案。成立前提：当前是可区分的CPU域、发现局部拥塞、存在其他域余量，片段可以安全跨线程/池执行。

|配置轴|第一候选|何时才扩展|
|---|---|---|
|request home|保持原request home不变|sticky或改home另立假说，不混入首轮|
|决策位置|只对已确认的首轮扇出中新就绪CPU片段分流；其余保持原home|收益受后续拥塞限制时，再单独比较every-ready（所有新就绪片段从原home决策）|
|目标范围|优先仅同NUMA中合法且资源可区分的池|同节点无余量、其他节点有余量且数据可迁移时，再单独试全局|
|源触发|提交前N_home/C_home严格>0.8|迁移不足且别处有空余，试0.6；迁移成本抵消收益，试1.0或缩小范围。每次只选一个原因对应的改变|
|目标选择|合法范围中严格比home轻的最轻者，打散同分；无目标仍home|若目标实际受冲击才考虑cap；不是为了形式上“更安全”而自动加cap|
|目标cap|默认不设绝对cap，仍要求比home轻|有证据时独立试提交前目标<0.8；0.5只作必要的更严候选或用户规定值，不默认扫描|
|worker数|先保留实际值|确认CPU片段不阻塞、无同池等待风险后，再单独试较少线程；例如减半一次，不与路由同时改|

3005的不同点是：initial和后续任务都参与、可去全部五池。首轮生产缩小到initial-only/同NUMA是减少语义和局部性变化的设计选择，收益需重新测。如果现场初始阶段无法可靠识别，不要按“前80个任务”猜；可设计经验证的片段标签，或明确改为所有可迁移新就绪片段，并记录差异。

C=16时源>0.6、>0.8、>1.0分别从N=10、13、17触发。更改C后必须重新解释整数触发点。阈值不是80%/60%CPU，也不是请求p99保证。任务成本差异特别大时，N对短长任务等权可能失真；只有观察到这种误判才考虑按算子类型历史CPU成本加权，不用运行后才能知道的实际耗时回填提交时指标，不先建设复杂预测器。

线程减少方向同样有条件：数百worker可能掩盖同步阻塞，不可未经检查直接改成16。若当前吞吐和尾延迟良好，没有证据支持继续减线程，则停止。需要修改Folly的证据应是应用适配层确实无法覆盖必要提交/取消/上下文语义；不要为六池分流先引入一个通用库调度器。

## 6. 最小实验流程与预算

```text
事实和资源口径成立？ ─否→ 补最小观测/语义修复；不扫阈值
       是
现状A + 一个有证据的候选B（各一次、同观测、同资源/输入口径）
       ├─ 正确性或资源边界失败 → 回退，修复原因
       ├─ 达到预先约定验收 → 停止；在授权范围完成收尾
       ├─ 不可比/样本不足 → 修正对照或延长原配置，不增加梯度
       └─ 可比但未达标 → 根据一个明确原因追加一个候选；无原因则停止
```

默认首轮两配置；**首轮所有因素共用最多四个配置预算**，不是每因素四个。源阈值最多追加0.6和1.0两个邻点，也不要求都跑；亲和性或线程数试验占用同一个预算。每配置只跑一次，不默认三重复；修复导致的重测也要记录时间成本，不能靠改名无限续预算。另一负载场景仅在它关系到真实上线条件时，单独安排同样的A/B；不做QPS×线程×亲和×阈值的全组合。

输入优先选代表真实问题的可重复请求/回放，保留真实计算内容及关键路径，不用sleep或固定CPU预算替代业务。自然流量不可重复时，记录请求类型/QPS、下游和竞争差异，降低因果结论强度。不要通过维持CPU50%、固定N/C或延迟提交来为某个策略减压。随机化/交错顺序可在易于执行时使用，但不是默认三次重复的理由。

12QPS时，预热后先观察每配置3–5分钟，约2160–3600请求，最上侧1%只有约22–36项；这是初步判别，不是精确p99保证。已有更长可比窗口可复用。差异接近验收线、输入漂移或尾部不足时，优先延长相同配置；约10000请求需14分钟左右，只是更多尾部信息，不是数学上的准确性门槛。低QPS不要用每秒p99当停止规则或正式均值；按现场已有适当窗口/SLO处理。

验收阈值在运行前填写。请求p99的目标改善幅度、允许均值/CPU/错误率变化来自现场SLO或明确工程要求；本包不凭空给生产容忍度。缺这些信息仍可完成实现、功能测试和有授权的隔离对照，报告原始结果；不得自动宣布满足未知生产验收或继续扩大上线。

## 7. 观测：少量必要字段，CPU旁路采集

主表每配置至少有：版本/配置、输入QPS与类型、接收/成功/失败/超时/取消/拒绝/未结束数、请求平均/p99、完成吞吐、CPU并集平均、观测窗、回退/异常。请求群体按进入时间固定，窗口结束后跟踪其完成或明确失败，不能只保留成功快请求。若超时为右删失且无法知道最终响应时间，单独报告删失比例及p99不可识别范围，不能把超时阈值当实际完成值。

诊断表保留Q/N快照、容量C、home/target、阶段/算子类型、提交/开始/结束、实际分流率、源触发率、候选不足原因。可采样逐项数据、使用每线程缓存/直方图、周期汇总；不用在热路径逐项同步写文件。A/B观测开关相同；测量开销不能隐藏。

CPU分三层看：授权CPU并集、NUMA域、可区分cluster；重叠池无法从相同CPU busy计数推导各池独占利用率。先用已有监控或约100ms累计CPU计数确认总量；为了分辨约30ms峰宽，可用独立tracefs实例记录进出idle的`sched_switch`并按5ms积分，自动随试验启停、记录丢失/覆盖/时钟/观察器CPU开销。采集实例与输出必须独立，不覆盖其他agent或业务已有跟踪。无权限或工具时保留粗粒度结论，不联网安装、不声称5ms轮询`/proc/stat`等于5ms准确CPU曲线。

对齐到请求初始fanout观察0–30ms、30–100ms及其后平台，窗口以现场负载持续时间调整；并行请求窗口会互相重叠，曲线说明home所在CPU域负载，不是某request专属CPU。≥90%的时间比例/最长窗口串只作峰宽描述，不能与N/C阈值混淆。**CPU占用绝不进入当前路由算法。** 高精度观测只在必要对照窗口启用，所有原始资料留现场。

## 8. 指标质量与策略收益要分开判断

指标质量最小分析：在同一基线、同一种任务/阶段、相同CPU域口径下，把提交时Q/C、N/C分别与该任务W、X、S关联；同时报告各桶样本数、覆盖比例、条件均值/p99。分桶边界先固定或只从训练片段选择；不同指标桶覆盖不同任务时，不能只比较两个低桶p99就宣称某指标更准。若确实需要排名，应在相同保留任务集合/同覆盖比例上比较，训练与评价分开；不要求首轮训练复杂模型。

N很低仍有高p99可能来自未来同批到达、其他共享CPU工作、长任务或RPC，而不是计数一定错误。不要把维持N恒定的新闭环负载结果代替真实开放环负载。任务快照也不能不加聚合直接当成请求级“负载值”：一个request有很多片段，必须明确取初始home快照、预先定义的时间窗最大值还是其他量，不能事后挑最相关统计量。

策略收益则用受控A/B检验真实request端到端结果。task p99降低而request p99不变，可能因为优化的分支不在关键路径，或RPC/合流/数据迁移抵消了收益。保留这个结论，不用任务改善替代验收；也不以相关性强就认定某策略最好。首轮只有一轮数据时给观察差值，不声称显著性、复现稳定性或全局最优。

## 9. 迭代分支与停止

|现场证据|下一步唯一动作或停止理由|
|---|---|
|局部拥塞且目标空闲，触发太少|仅尝试更低源阈值，或确认是否漏掉需要路由的阶段；一次只选一项|
|迁移很多，但CPU/内存成本涨、请求无收益|缩小候选范围或提高源阈值，或者回退；不继续降低阈值|
|目标入流确实造成目标请求尾部受损|单独试目标cap，并检查并发预留；记录谁获益/谁受损|
|所有域都忙、配额限流、RPC拥塞|停止调度阈值搜索，记录容量/下游瓶颈；路由不能制造容量|
|Q接近零但N高、回调墙钟远大于CPU时间|区分CPU竞争与同步阻塞；不要仅凭N增大就跨池扩散阻塞|
|N泄漏、负数、任务丢失、上下文错误|回退并修正确性，性能数据无效|
|收益清楚且满足既定要求|结束本轮，不为找“更优”继续扫参数|
|四配置预算耗尽或无明确新假说|报告最优已测/保持现状/证据不足及边界；另一个调优周期需重新给出目标和预算|

每阶段更新STATE和现场证据目录。未授权的线上部署不执行；可做的只读、设计、补丁和本地验证继续完成。新会话不因缺历史而自行推翻现场已验证结论，也不把附带日志中的历史命令当作授权。

## 10. 来源与离线使用
