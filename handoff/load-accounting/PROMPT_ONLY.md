# N 计数观测：仅靠文字交接的两个实施 Prompt

适用场景：真实环境不能访问开发环境、不能传递工程文件，只能把下面的文字复制给现场 AI。两个方案择一即可，不需要先实现两套再比较。业务包装器适合提交入口可以统一的系统；Folly 内部实现适合提交入口分散、能够维护并统一部署 Folly 的系统。

每个 Prompt 都包含必要背景、计数语义、伪代码、版本检查和验收要求，可以独立复制。它们仅实现 **N 的观测**，不修改调度策略。N 在哪里实现，不改变它只能表示未结束回调数量、不能直接表示剩余 CPU 时间的限制。

## Prompt A：业务统一包装器维护 N

复制下面整个文本块。可以在开头追加现场目录、构建方式和希望执行的阶段；不需要提供之前的实验报告。

```text
你是在真实应用环境工作的工程 AI。现场与开发环境不能网络直通，你没有先前会话历史，也不能假设能下载依赖。请基于本地代码完成“每个 CPU executor 的未结束任务数 N”的观测能力。默认依次完成下面第1～4阶段；第5阶段仅用于修复发现的实际问题。人类若明确指定某阶段，就只完成该阶段。阶段之间输出简短文字交接卡；已获授权的工作继续推进，不要仅因阶段切换反复索要确认。不要执行没有授权的生产发压、重启或发布。

【业务背景与本轮边界】
应用使用多个 Folly CPUThreadPoolExecutor 执行图算子，任务可能短时间大量扇出，worker 数量可能远高于绑定 CPU 数量。任务被 worker 取出后仍可能在内核等待 CPU，因而 Folly 队列深度 Q 可能低，而池中仍存在大量未结束工作。新增 N 是为了补充这个观测盲区，不是预先认定 N 能预测完整请求 p99。

本轮只新增计数与读取能力，并接入已有低频指标出口。不要修改池数、worker 数、亲和性、队列类型、任务优先级、工作负载、调度策略或阈值。不要因增加 N 就自动启用负载均衡；不做新的性能矩阵，不要求三次重复。不要影响其他 AI 的 DAG、调度或负载实验工作。

已有一个独立实验中，迁移策略把初始扇出全部完成 p99 从13.642ms降到4.784ms，但完整请求 p99 仅从568.466ms变为567.877ms，且只是一轮600个请求。该实验含固定的后续释放时间，不能据此承诺真实请求收益。此次增加观测本身更不能预期降低时延。

【N 的唯一语义】
N[p] = 已为池 p 预留提交、尚未终结的 CPU 执行回调数量。
计数单位是一次 executor 回调，不是 request、线程或包含异步等待的完整算子。
必须在任务对 worker 可见之前 N++。排队、已领取、等待 CPU、执行和被抢占期间都保留计数；正常结束、异常结束、过期处理结束或确定永久丢弃时恰好释放一次。预留后若提交未被接纳，必须回滚。未就绪图节点、尚未到释放时间的工作不计入。
异步 RPC：发起 RPC 的 CPU 回调返回时释放；网络等待期间不计；响应后提交的新 CPU 回调重新计数。同步 RPC、锁等待或 sleep 若发生在回调内部，仍占一个 N，这会污染“CPU需求”的解释，需要记录而不是偷偷改语义。
计数仅用于观测，因此原子数值读写可用 relaxed；普通非原子变量的并发访问不可接受。N++/N-- 不能依赖采样。即使采样允许误差，也不能漏掉任务生命周期。
N 与 Q、active、线程数不同。不要用 Q+active 代替 N，不要把 Folly 任务队列与内核 runq 混为一谈。先提供 N 的原始计数；若展示 N/C，必须记录 C 来自哪组 CPU 及采用逻辑CPU还是有效容量，N/C不是CPU利用率。

【第1阶段：探索，输出可核对的事实】
1. 查阅本地仓库指导文件、git状态、构建目标及实际链接的 Folly 版本。避免覆盖未提交修改；必要时建立隔离开发位置。不要假设源码目录就是运行时链接版本。
2. 找全普通 add、addWithPriority、带 expiration/expireCallback 的 add、Future continuation、直接访问原 executor 等提交入口。确认能否都经过同一业务包装器，列出绕过入口及无法覆盖的任务范围。
3. 跟踪队列接纳、执行、异常、过期、取消、清空、stop/join、缩容、executor销毁、KeepAlive 所有权。区分“发出取消信号”和“工作确实终结”。确认关闭时是排空还是丢弃，过期时哪些闭包被销毁、哪一个被执行。
4. 找到已有指标导出线程及生命周期管理，确认包装器不能先于提交者或未结束任务失效。不得在每次提交中增加 /proc 读取、日志、时间戳或线程扫描。
5. 输出：实际版本/编译链接来源、提交调用图、每条终结路径、计数覆盖范围、最小修改文件清单、未确认点。未知问题先保留并继续不依赖它的工作，不编造结论。

【第2阶段：设计】
新增统一入口，例如 TrackedCpuExecutor。所有受统计的工作走它；每池持有 CounterState{atomic<size_t> N}。接口建议为 Optional<size_t> getOutstandingTaskCount()：默认关闭，构造时显式enabled=true才启用；未启用返回空，启用且无工作返回0。采用现场支持的 folly::Optional 或 std::optional，禁止把“未启用/不支持”当作0或空闲。不支持运行期间任意切换，除非设计了清晰的排空与状态转换协议。

使用随任务移动的计数凭证，避免在业务算子各处手写 N++/N--。每池 CounterState 的寿命覆盖所有凭证，可由 shared_ptr 持有；不得让任务持有指向已析构包装器的裸计数地址。包装器继续遵守原 executor 和 KeepAlive 的寿命约定，不能只因计数状态安全就认为 executor 本体安全。
每个真实池只有一个统一计数包装；应在接收任务前建立，或排空旧入口再切换，不能追溯统计包装建立前的任务。此组合式样例不是folly::Executor的可替换对象，不实现其KeepAlive协议；要求Executor*或Future自动投递的接口必须逐一接入，不能强制转换或返回原pool后宣称全部覆盖。

普通 add 可以采用无每任务独立堆分配的 move-only Ticket：
  Ticket(state): 保存 shared_ptr<CounterState>; state.N.fetch_add(1, relaxed)
  move(Ticket): 只转移所有权，不重复增加N；源票据变空
  finish(): 把持有的state移到局部；若非空，state.N.fetch_sub(1, relaxed)
  ~Ticket(): finish()
  wrapped(task, ticket):
      scope_exit { ticket.finish(); }
      task()  // 原异常行为保持，退出时仍完成计数
  submit(task):
      若未启用，直接调用原路径
      先构造Ticket，再将Ticket移进wrapped
      原executor.add(move(wrapped))

“析构兜底”用于提交未接纳或未执行即丢弃；“回调退出主动finish”用于已执行终结，不能一直等闭包最终销毁才释放。若需要移动赋值，必须先释放自身旧凭证再接管新凭证，避免覆盖漏计；普通闭包样例不需要时可明确删除移动赋值。

带expiration的路径有正常/过期两个闭包，应共享同一个终态预留，不能各自N++，也不能在正常闭包被清空时提前N--而过期回调还在运行：
  SharedLease(state): 内含一个Ticket，atomic<bool> finished=false
  finishOnce(): if !finished.exchange(true, relaxed): ticket.finish()
  ~SharedLease(): finishOnce()
  submitWithExpiration(task, expiry, onExpire):
      lease = make_shared<SharedLease>(state)  // 仅一个逻辑任务，一次N++
      normal = [lease,task] { scope_exit lease.finishOnce(); task(); }
      expired = [lease,onExpire] {
          scope_exit lease.finishOnce();
          if onExpire存在: onExpire();
      }
      原executor.add(move(normal), expiry, move(expired))

即使业务没有过期处理函数，也要覆盖“正常函数被跳过”的终结路径。检查 expiry=0 时原版本的行为。上面是语义示意，需根据现场真实签名与移动规则落地。
参考包装样例在计数前拒绝空用户函数和负过期时间，expiry=0走普通任务路径；现场若依赖不同约定，先说明兼容性选择。包装器在用户回调体退出时释放，包含用户过期回调，但不覆盖其后Folly taskProcessed观察者、RequestContext清理或任意捕获对象析构；Folly内部版本可覆盖更外围runTask区间，比较两种N时必须说明边界差异。

提交抛异常时不能未经审计就无条件手动N--：对于版本差异或自定义队列，要确认此异常是否保证未接纳。优先让凭证跟随任务所有权：未接纳对象销毁会释放；若已被接纳，其所有者继续保留凭证。不得额外catch回滚造成双减或运行中提前减。正常/过期两条路径共享终态，拒绝/丢弃也只能释放一次。

如现场任务可能被抽取出队后转交其他 executor，明确这是同一执行任务的所有权转移还是新的提交，防止重复计数或长期归属旧池；本轮不新增这种迁移行为。

给出成本说明：普通路径每任务两次N原子读改写，并存在每池 shared_ptr 引用计数与凭证尺寸成本；过期双闭包路径还可能需要每任务一次共享lease堆分配和一次终态原子交换。不能声称“完全零成本”。如实现先统一采用共享lease以减少复杂度，必须明确普通任务也承担该成本；仅在证据需要时再加入move-only快路径。

【第3阶段：实现】
只改统一包装器、必要接入点、最小测试和使用说明。保持提交签名、优先级、过期行为、RequestContext、KeepAlive和异常传播兼容；无法透明转发的接口明确列出。指标带 enabled/available 状态，采样调用一次原子load，复用已有监控周期；不为每任务打印记录。
多生产者下原子计数应正确，但“读取各池N→比较→向目标提交”不是事务，多个生产者可能同时选择同一池。此次不修改选池、不新增CAS接纳上限。

【第4阶段：最小验收】
使用latch/baton或明确同步构造稳定状态，避免靠sleep猜测计数；运行必要单测和既有相关回归，不扩大矩阵：
1. 未启用返回空；启用空闲为0；原有行为与配置不变。
2. worker被阻塞、队列有任务时，验证N同时包含已执行但未结束者和排队者；进入回调不减，全部终结后归零。
3. 快速回调、多生产者、提交与完成交错：静止检查点计数精确，无下溢、无泄漏；不要要求任意多个独立快照满足一致性等式。
4. 正常和抛异常回调各释放一次；业务异常语义保持。
5. 已确定未接纳的拒绝、未执行丢弃、过期且有/无过期回调：均不泄漏；过期回调阻塞时仍计入N。
6. 包装器关闭/底层排空或丢弃：状态寿命安全；不要武断要求stop返回就N=0。若现场没有某条路径，说明不适用与证据，不能伪称已测。
7. 对接入前后计数范围做审计，报告仍绕过包装器的工作。

如已有现场授权，才做一个固定工作负载的观测off/on对照：资源、策略、亲和、输入、线程数保持一致，运行顺序和时间记录清楚。比较请求级完成mean/p99、吞吐、失败率和CPU，同时检查N；任务级指标仅辅助。不得把计数观测开关误写成均衡开关，不要求三次重复。若暂不能发压，交付准确命令和待执行项，不伪造测量或宣称无开销。

【第5阶段：仅针对发现的问题修正】
只有正确性失败、无法覆盖真实入口或观测成本超过现场已有预算时才修正，修改后重跑受影响检查。不要借机寻找最优阈值、增加负载场景或改DAG设计。没有预算时先报告测量，不自行编造“可接受”阈值。

【每阶段的文字交接卡；后续agent无需原会话也能继续】
每阶段结束都填写以下字段，禁止仅写“见上文”或依赖外网链接：
任务与边界：只为每池CPU回调增加N观测，不改调度/阈值/亲和/线程/负载。
语义：预留先于提交可见；排队和执行都计入；全部终结路径恰好释放一次；未启用为空。
现场版本与来源：应用/Folly commit或包版本、源码与实际链接库路径、编译命令。
当前位置：目录、分支、已完成阶段、已修改文件、未提交变更归属。
实现摘要：覆盖的提交入口、普通/过期票据方案、CounterState寿命、关闭与拒绝语义。
证据：实际执行的命令、退出码、测试通过/失败/未执行项；性能数据注明真实运行条件。
未决问题与风险：明确哪些生命周期或版本差异尚未核对，不能用假设填补。
下一步：下一阶段编号、具体文件/检查项/命令、已获授权范围；不要请求重复授权。
复现与回滚：如何构建、启用/关闭观测、恢复本次修改；不能影响其他人的变更。
```

## Prompt B：Folly 内部维护 N

复制下面整个文本块。它给出了本地参考版本的修改位置，但现场 AI 必须先沿现场源码验证；不要求现场能够获取参考仓库或补丁。

```text
你是在真实应用环境工作的工程 AI。请给现场 Folly CPUThreadPoolExecutor 增加可选的“未结束任务数 N”观测。现场不能连接开发环境，你没有先前会话上下文，也不能假设能下载依赖。本文是完整设计参考，不要求获取外部文件。默认依次完成第1～4阶段，第5阶段只修复实际问题；人类指定阶段时遵从指定。每阶段形成文字交接卡，在已授权范围继续推进，不为阶段切换反复请求确认。没有授权不执行生产发压、重启或发布。

【背景、范围与禁止事项】
应用有多个CPU线程池，短时间扇出大量任务，线程数可能远多于CPU。Q只覆盖仍在Folly队列中的工作；已领取但未结束的工作仍会争抢CPU。新增N用于观测这部分工作，不能将它直接解释为CPU利用率或剩余CPU时间。
本轮仅改计数、只读接口、配置和必要验证。不要调整调度策略/阈值、池数、线程数、CPU亲和、队列类型、负载或DAG；不要扩大性能矩阵或要求三次重复；不要覆盖其他agent的工作。阈值0.8/0.5等不是此次目标，也不应固化进Folly。
已有独立实验里，初始扇出集合p99从13.642ms降到4.784ms，而完整请求p99只从568.466ms变为567.877ms；这是一次600请求、含固定后续释放窗口的实验，不能推出普遍收益。增加计数自身没有降低请求时延的承诺。

【定义必须保持一致】
N[p]是分配给池p、已预留提交、尚未终结的普通CPU执行回调数。N++必须早于入队可见；队列等待、被领取、等待CPU、执行和抢占都保留。正常执行结束、异常结束、过期处理结束、提交未接纳或永久丢弃，恰好释放一次。内部poison/停止标记不算普通工作。
未ready图节点、未到释放时间的任务、异步RPC网络等待不计入。异步发起回调返回后释放，响应提交的新回调重新计数。同步RPC或锁等待仍计入N，要报告这一限制。未启用不等于0；未知或不支持不能解释为空闲。
不通过Q+active拼N，不扫描线程，不依赖/proc，不把Folly队列和内核runq混淆。N/C若导出，C来自部署配置且必须解释，N/C不是利用率。每次任务的计数维护必须准确，观测快照可以暂时陈旧；普通变量并发访问不能以“容忍误差”为理由使用。

【参考版本与适配原则】
开发侧参考的是Folly tag v2026.10.26.00、commit c8c7adb72c6d73e2fced5ff5cebc96aa3ff65b2c；参考CPU线程池相关代码与4d7cc97对应代码相同。现场版本可能不同，这些标识只用于说明来源，不是必须下载的版本要求，不要因此升级现场Folly。
在参考源码中，改动涉及：
  folly/executors/CPUThreadPoolExecutor.h
  folly/executors/CPUThreadPoolExecutor.cpp
  folly/executors/test/CPUThreadPoolExecutorOutstandingTest.cpp 为新增定向测试
  folly/executors/test/ThreadPoolExecutorTest.cpp 为既有相关回归，或现场等价测试
  ThreadPoolExecutor.cpp仅用于核对runTask生命周期，通常无须改通用父类。
按函数职责和所有权关系适配，不按行号，不盲贴patch。先确认现场CPUTask、addImpl、threadRun、runTask是否仍具备对应职责。

【第1阶段：探索】
1. 检查仓库指导文件、git状态及其他人的变更，隔离本次工作。记录真实源码版本、构建安装位置、应用头文件来源和实际链接库；不要只看当前目录的tag。
2. 找全CPUThreadPoolExecutor构造函数及Options传递链，普通add、addWithPriority、带expiration/expireCallback的add和自定义队列接口。确认所有普通任务能在一个公共入口预留。
3. 跟踪CPUTask的构造、移动构造、移动赋值、析构；队列move/noexcept约束；worker局部Optional如何take、复用、销毁；runTask是否移动清空正常/过期闭包。找全拒绝、抛异常、过期、丢弃、stop/join、缩容、poison、KeepAlive路径。
4. 特别检查入队后生命周期。参考addImpl源码明确警告：任务入队后可能迅速执行完，释放最后一个KeepAlive，从而推动executor关闭；不得新增未经保护的入队后this访问。某条路径需要访问时应遵守原有KeepAlive设计。
5. 核对TaskObserver：参考版本的taskEnqueued在真正入队之前通知，未执行即丢弃也缺少与taskProcessed成对的终结通知。仅把这两个事件相减不足以实现完整N。现场版本若不同，也必须证明全部异常/丢弃配对，不能凭命名判断。
6. 输出调用图、状态表、版本差异、全部计数入口/出口、最小修改列表。缺失源码、工具或依赖如实记录；继续可独立完成的审计，不虚构测试。

【第2阶段：设计API与所有权】
新增Options::setTaskCounting(bool)，默认false；新增只读Optional<size_t> getOutstandingTaskCount() const。使用现场项目的optional类型，例如folly::Optional；禁用返回none，启用且无工作返回0。固定在构造时启用，不擅自支持运行期间切换。所有构造/委托路径正确传递选项，含优先级队列和自定义队列。
每个启用的池创建一个共享CounterState{atomic<size_t> value{0}}。CPUTask新增一个move-only票据，持有共享CounterState；只为每池分配状态，不为每个任务独立分配票据。票据直接作为任务成员，移动只转移所有权，析构兜底释放，主动release可重复调用但只有第一次减数。CountState必须活得比所有队列及worker中票据长；不要依赖executor成员的析构顺序或任务是否可能被外部queue抽取。

核心伪代码：
  struct CounterState { atomic<size_t> value{0}; };
  class TaskTicket {
      shared_ptr<CounterState> state;
      acquire(shared_ptr<CounterState> s) {
          assert当前无票据;
          state=move(s);
          if(state) state->value.fetch_add(1, relaxed);
      }
      release() {
          auto s=move(state);
          if(s) s->value.fetch_sub(1, relaxed);
      }
      move_construct(other): state=move(other.state);
      move_assign(other): if(this!=&other) { release(); state=move(other.state); }
      destructor: release();
      copy: 禁止;
  };

  CPUTask:
      保留原来的Task继承、优先级、queue observer等成员
      新增TaskTicket accountingTicket
      确认默认/poison构造不acquire
      确认全部move路径转移票据，符合队列noexcept要求

  CPUThreadPoolExecutor构造:
      若Options.taskCounting: state=make_shared<CounterState>()
      否则state为空

  getOutstandingTaskCount():
      if state为空: return none
      return state->value.load(relaxed)

  addImpl(enqueueTask, task):
      保留原先空函数/poison检查，空函数不计数
      task.accountingTicket.acquire(state)  // 在真正入队之前
      保留原有observer、KeepAlive、动态worker等逻辑
      enqueueTask(move(task))
      不新增未经KeepAlive保护的入队后this访问

  threadRun处理普通task:
      scope_exit { task.accountingTicket.release(); }
      runTask(thread, move(task))
      // 正常、异常被runTask捕获、过期回调执行结束，都在这里终结
      // guard要在task被reset/覆盖/销毁之前执行，具体按现场局部变量作用域适配

  未执行任务被销毁:
      TaskTicket析构释放；已主动释放的票据为空，不会双减

原子使用relaxed是因为计数不承担任务数据发布或结果同步。不要用计数为0替代join/KeepAlive/既有关闭协议：其他生产者仍可能提交。读取接口也要求调用时executor本体仍有效，CounterState共享不保证调用已析构executor的方法安全。

若add抛异常，凭证继续跟随实际任务所有权。未接纳时持有任务的对象销毁便释放；已经被某个有效所有者接纳时继续保留。跨版本或自定义队列不能未经审计就假定所有抛异常都表示未接纳，不要加一个无条件catch N--。对于既有异常语义本身不清楚的队列，记录并补针对性测试；不要编造参考版本内部会抛出的异常。

正常回调与expireCallback都由同一个CPUTask票据覆盖。释放点放在runTask外围，保证正常闭包清空时不会提前释放而过期回调仍执行。必须确保runTask中并未把票据移到其他对象；若版本会移动完整任务，则调整为在真正持有票据的对象上释放。
stop返回时可能仍有未丢弃的排队任务；不要强行清零。保持原本stop/join语义，任务真正销毁或完成才释放。poison直接进队列时不能误计；其他可执行的内部工作若通过普通add提交则按已声明范围统计。

成本应诚实说明：启用时每普通任务两次计数原子读改写、共享每池状态的引用计数与任务成员尺寸开销；读取一次原子load。不为每个任务独立堆分配票据不等于整个路径零分配。禁用时避免计数原子操作和状态分配，但新增成员仍影响CPUTask尺寸，不能承诺零影响。

【第3阶段：实现与版本迁移】
实现选项、每池状态、任务票据、统一预留、普通执行路径释放、析构兜底、接口及测试。不改ThreadPoolExecutor通用active语义，不将N写入所有executor类型。审计所有构造重载，避免某个重载漏启用或选项被覆盖。
修改CPUTask布局/Options/API可能改变ABI，明确要求重编Folly及全部受影响消费者、自定义BlockingQueue<CPUTask>实现/插件；不要混用新头文件旧库，也不要假设不同版本导出的符号兼容。CMake/Buck等只更新现场使用且确有需要的构建项，不能宣称未执行的构建通过。
示例调用可以是Options().setTaskCounting(true)，随后检查getOutstandingTaskCount()是否有值，再导出N；若现场构造签名不同，给出真实签名。采样接入现有指标周期，禁止每任务读取/proc或打印日志。多生产者计数准确不代表多池读取、选池、预留是原子事务；本轮不实现负载均衡。

【第4阶段：最小验收】
用latch/baton等同步保证观察时状态确定，运行新增针对性测试与已有CPU线程池相关测试。最少覆盖：
1. 默认禁用返回none，启用空闲为0；主要构造重载/优先级/自定义队列路径可用。
2. 一个worker在回调中阻塞、若干任务排队，N覆盖两者；出队/开始执行不减，全部完成后归零。
3. 正常、异常、快速完成与多生产者交错无泄漏或下溢；计数在任务可见前已增加。
4. 明确未接纳的拒绝、预留后异常、未执行丢弃、CPUTask移动/覆盖均恰好释放一次。
5. 过期且有/无expireCallback；过期回调仍阻塞时N保持，结束后释放。
6. join排空、stop保留/丢弃、poison和析构；按真实实现判断预期，不要求stop即时归零。保留外部队列/任务引用时状态仍安全。
7. KeepAlive与快速执行关闭场景没有新增use-after-free；按现场可用工具使用已有sanitizer配置，不强求下载新工具。
8. 验证消费者实际链接新库，保留功能行为和异常语义。

如果已获现场发压授权，仅做一个固定输入的计数off/on对照，资源、调度、亲和、线程和负载保持相同。记录运行条件与顺序，比较业务请求完成mean/p99、吞吐、失败、CPU，并观察N。一次结果只描述本次观测开销，不论证负载均衡收益，不要求三次重复。现场未授权或不能执行时给出可运行命令及未验证项，不能报告不存在的数值。

【第5阶段：仅必要修正】
仅因计数不正确、版本不兼容、覆盖缺失或实际观测成本问题而修改，重跑相关检查即可。没有证据不要延伸到阈值梯度、DAG、更多负载场景。若变更会超出本轮边界，输出独立后续建议，而不是偷偷实施。
```

## 使用与交接注意

- 现场若只允许探索，可在任一主 Prompt 前加“本次仅执行第1阶段，不修改代码”；若希望连续完成，保留默认阶段安排。
- 若更换 AI，可把对应完整主 Prompt 与最新交接卡一起复制过去；交接卡必须包含现场具体路径、版本和实测结果，不能只写“如上”。
- 两个方案统计范围可能不同：包装器只覆盖经过它的任务，库内计数覆盖该池接纳的全部普通任务。对比或迁移前先确认范围，不能将漏计误解成更低负载。
- 此交付不把 N 判定为最终负载指标，也不授权开启迁移。指标质量与调度收益需在其后的独立任务中判断。
