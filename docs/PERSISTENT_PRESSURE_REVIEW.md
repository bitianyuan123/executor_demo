# 持续压力门控：外部分析审阅与候选策略设计

**当前状态：4016 SD六轮已完成，见[最新审阅](TARGET_V2_4016_REVIEW.md)。当前仅按[既有SD结果的到达核查指南](TARGET_V2_4016_NEXT.md)，用`arrival_audit.py`对已完成六个目录做只读、有界核查；无新增压力、trace或阈值试验。暂停扩大CPU工作族性能矩阵；后续工程优先实现等待期间释放executor worker、完成后重新提交恢复回调的异步工作族。v2驱动当前尚未实现该工作族，没有可执行的异步负载CLI。持续压力门控仍未实现；下文保留候选论证与历史决策，不将3ms设为默认。**

## 1. 结论和当前执行顺序

用户转述另一agent的分析：单池激活约8900次/s、平均N约7.8，1266段“过载”按最终峰值分组；建议超过0.9C持续3ms才借出，超过2C立即旁路，低于0.75C退出，按平滑目标负载选池。**这是未人工复核的假设，不是新验收结果。** 原分析代码、N定义、分组计数与完整模拟输出尚未收到；“16%恶化到29-”为截断文本，不能补出其完整数值。

判断：持续性门控值得加入候选设计；当前证据不支持把3ms、0.9C、0.75C、2C设为默认，也不支持认定所有1～2ms尖峰都应留在本池。先补有界、可复算的口径和在线预测价值，再决定实现。当前运行策略保持不变。[4007/4008](TARGET_V2_4008_REVIEW.md)完成历史窗口与task异质性；[4009](TARGET_V2_4009_REVIEW.md)又完成burst竞争，持续重选出现约1%的小幅收益。当前先做[真实负载校准](WORKLOAD_FIDELITY_PROTOCOL.md)，不因合成场景变化直接启用时间门控。

目标始终是所选硬件cluster各一池，当前六cluster六池。历史四池未绑CPU的轨迹仅提供现象和算法假设，不重映射为六池，不拿历史单池时长当作16逻辑CPU绑定后的消化速度。

## 2. Little公式没有证明算子0.85ms或1.2ms排空

算术是`7.8/8900秒 ≈ 0.876ms`。是否可解释为平均驻留，取决于N和进入率是否描述同一对象、同一系统边界、同一生命周期，以及时间平均、窗口边界和未闭合记录如何处理。不能用waking次数作Folly任务到达，再把onCPU或unique线程数作任务系统中的N。[Little原始论文](https://bpb-us-e1.wpmucdn.com/sites.mit.edu/dist/9/2055/files/2020/05/ContentServer.pdf)定义了这些对应关系，并说明有限观察窗口的边界贡献。

| 若N实际是 | 对8900的要求及能得到什么 |
|---|---|
| 窗口unique-onCPU | 不是瞬时系统占用N，不能直接代入得到驻留时间 |
| 时间加权的onCPU线程数 | 需匹配相同运行区间的进入计数；用wake率通常不等于平均算子CPU时间 |
| runnable+running线程数 | 需对应完整唤醒到再次阻塞的生命周期、去重及边界；最多得到线程活跃周期，不是算子时间 |
| 已接纳未完成的算子O | 需要用户态任务接纳/完成事件，现有五种sched事件并未提供 |

Linux的waking、wakeup描述线程唤醒过程，并不携带业务算子身份。[内核事件定义](https://github.com/torvalds/linux/blob/v6.6/include/trace/events/sched.h)可用于核对语义，目标内核仍需核对版本。一次唤醒可以连续执行多个Folly任务，一个任务也可能多次睡眠/恢复；不能建立一一对应。

即便额外假设每任务纯CPU耗时恰为0.876ms、20个任务同时到达空的16槽系统、没有新到达或开销，`20×0.876/16≈1.095ms`也只是总工作/总服务能力的理想下界。对20个等长、不可拆分、非抢占任务，最后4个第二批执行，全部完成约`2×0.876=1.753ms`。这只是反例，不是对真实机器的新预测。不同长尾、剩余工作、SMT效率会改变结果；长周期均值不能预测一次突发清空时间。

特别是历史未绑CPU池短时使用过远超16个逻辑CPU的服务能力，其迅速消化可能正依赖这些额外资源。“1ms后都消耗掉”不能作为目前已经证实的结论，更不能据此取消目标cluster的初始扇出借出。

## 3. 持续时间表和EWMA模拟还缺什么

1. **最终峰值含未来信息。** 按整段最终峰值≤20/>20分组，可作描述性分类；在线决策不知道未来峰值。要验证的是“当前N、已经持续a毫秒”之后还有多少剩余压力，不是整段最终持续多久。持续3.1ms的事件，在第3ms确认后仅剩0.1ms。
2. **事件定义必须与算法一致。** 如果1266段按N>16开始，新算法却从N>14.4计时，两者的持续分布不同。要给起止阈值、是否合并短间隙、逐池计数和首尾删失。1ms固定桶的1/2/3ms分类受对齐和取整影响，不能当精确状态转移时间；各百分比的舍入也不能替代整数计数。
3. **事件多数不是成本多数。** 92%的事件短，不表示92%的等待时间或受影响请求也来自短事件。应另报事件数加权与压力时间/超额面积加权；如果N不是可积分的状态量，就不要计算“超额需求面积”。持续性也不是唯一判据，剩余工作、可借资源、迁移代价和关键路径都影响收益。
4. **未绑CPU轨迹没有16CPU硬上限。** 历史N>16或>32只是相对目标名义容量的描述，不证明历史发生相同排队，也不等于绑定后的反事实压力。
5. **EWMA滞后方向合理，具体浪费率未验证。** 原N(t)上重放阈值只会改变模拟决策，不改变后续N、目标池竞争或缓存。它可以检验响应/残留时间，不能直接给请求时延、CPU浪费或迁移收益。若要闭环模拟，需要外生任务到达、服务需求、依赖和资源模型，不能拿旧N(t)当各种策略下不变的输入结果。
6. **N≤C不是“迁移浪费”的真值。** 新任务或新chunk加入后可能排队；反之N>C若包含阻塞callback，也不证明CPU忙。需给该比例的分子/分母、按时间还是按决策、评估时点是接纳前还是后、是否包含本次预留量，不能将代理错误率等同业务损失。

补证只需原agent在测试机打印约80行摘要；优先复用已有中间产物和原分析代码。具体可复制的任务说明见[持续性审计提示词](TRACE_DURATION_AUDIT_PROMPT.md)。不要求上传大trace，也不以旧轨迹补齐为目标实验前置条件。现有`analyze_sched_windows.py`的连续高onCPU桶不能替代尚未定义的N或精确runnable事件分析。

## 4. 候选策略应怎样收紧定义

这套思路可称“延迟确认、即时退出、严重压力旁路”。必须把**测什么、何时允许借出、借到哪里、后继归属**分开：

`LoadProvider/LoadScorer → 确定preferred亲和池 → PressureGate → 候选当前负载/同NUMA优先/收益判断 → reservation与提交`。

现有Provider/Scorer继续复用；新增PressureGate是候选设计，**尚未实现**。不把状态计时塞进负载数值，使读取单位和目标评分难以解释。先固定一种计数信号如O/C做实验，其他Q/I保持诊断；不能直接把历史N换成O。还须明确计时信号是裸O还是含预留R的评分：现有outstanding评分为(O+R)/C，接纳到释放预留之间可能短暂重复覆盖，不能将其当作严格生命周期计数N。work评分单位为估计CPU微秒/容量，不能沿用任务数阈值。

建议规范如下，数值均保留可配，以下是待验证方案而非默认设置：

| 状态/动作 | 明确语义 |
|---|---|
| Idle→Pending | 当前信号超过start；记录有效观察起点 |
| Pending继续/复位 | 必须定义压力持续性；若采用连续超过start的含义，下降到≤start就清零，即使尚未低于release |
| Pending→Armed | 同一未复位、未超过max-gap的高压段观察跨度达到hold，且当前压力仍满足条件 |
| Armed退出 | 当前值低于release时立即禁止新的压力借出；在release到start之间保留滞回是否继续借出要显式规定 |
| emergency | 当前值超过emergency时可跳过hold；不得绕过pin、balance-at=fork/NonFork、NUMA权限、hop、目标保护及收益条件。是否将Armed锁存必须单独定义；首个原型可只对本次旁路，不因一个极短尖峰永久延长门控状态 |
| 无有效历史 | 陈旧/丢观察时不凭旧busySince宣称持续压力；清计时或退回明确配置的即时策略，记录原因 |

若取start=.9C、release=.75C，则N约15持续3ms就可能触发，而Armed在N=12～16时仍可能保持；它是在预留余量与滞回之间权衡，不能叫“只在确有排队时触发、无排队立即关闭”。C=16是逻辑CPU归一化容量，不保证SMT吞吐等于16物理核。

**快释放不是立即回home。** 它只停止此preferred池的新借出；已经迁出去的分支是否留parent还是回request home，由ContinuationPolicy决定。目前`return-low=.5`是home回迁门槛，不能复用为pressure-release参数，否则同时改变两件事。

**平滑值不能独自决定目标。** 候选设计先用当前有效信号、本次chunk及预留量排除不合适目标，再在同NUMA的合格候选中排序；跨NUMA仍受开关、代价和收益约束。EWMA可作为后续排序对照，不能忽略目标刚发生的新突发。并发发送方同选一个低分目标仍可能集中投递，预留量只能缓解，不能宣称完全避免。当前choose接口尚未接收本次chunk大小，只能看到此前已发布的预留；完整的本次chunk前瞻保护需要扩展选择上下文，不是现有能力。

“home平手优先”也要独立测试：当前parent模式以实际父池为preferred，相同分数不自动迁走。强制home优先会混入亲和策略变化，不宜与新门控一起调整。

## 5. 连续性怎样观测，成本怎样控制

4008旧CSV样例的首波提交跨度均值仅0.070～0.120ms，callback跨度均值约29～67ms；两者都不是内核连续饱和时间，但证实了需要区分提交机会与后续排空。当前`RequestExecutor::choose()`只在新任务提交时运行。若一批20任务在0.2ms内全部入队，即便压力持续5ms，第3ms也没有新的提交让路由器采取行动。该门控不会主动搬已排队或运行中的工作。对于80分支，计数又可能迅速超过2C，直接走emergency，反而几乎测不到3ms逻辑。因此必须统计“持续触发时还有多少新ready任务可路由”，而非只看门控开启时间。

两次add的高读数相隔3ms，不证明中间持续高压；中间可能已归零后再次突发。可实现方向及成本：

| 观测实现 | 成本和准确性 |
|---|---|
| 只在提交读计数/时钟 | 成本相对可控，但仅是提交采样门控，不能证明无提交区间连续性；需最大间隔、计时失效与退回规则 |
| 生命周期变化维护压力状态 | 覆盖accepted、完成、失败回滚和预留变化；计数/时间戳/代际必须有一致顺序。两个独立atomic写可能让旧完成reset覆盖新突发开始，不能未经并发验证声称正确或零扰动 |
| 单写者定期读各池已有计数并发布 | 原型较易审计；采样成本随池数而非worker数增长，不扫/proc。仍是采样近似，需实际间隔/最大gap/有效率；热路径再读当前信号处理快速退出、emergency及目标保护 |

定期计数采样与现有50ms扫描数百TID的CPU后端不同，不能把后者改为亚毫秒扫描来实现门控。原型可研究例如0.1/0.5ms计数采样，但这些只是开销/分辨率试验点；短尖峰可能落在采样间隙内，不能把“未见下降”称为已证明连续。

候选参数至少分开：gate模式、pressure-signal、start-ratio、release-ratio、emergency-ratio、hold-us、sample-period-us、max-gap-us、emergency是否锁存、目标当前值保护与可选EWMA、tie-break。每个任务路径增加时钟、原子或后台发布都会有代价；需trace0/1之外的gate/采样开关对照，报告每提交成本和整轮CPU/时延。

CoDel可借鉴“持续延迟超过目标才动作、及时重置”的思想。它实际观察网络包sojourn time，并用持续高于目标的状态识别持久排队；不是对线程数做EWMA，也不是线程池负载均衡器。不能搬用其参数、网络反馈时间或无锁结论到多生产者/多worker总池。[RFC 8289](https://www.rfc-editor.org/rfc/rfc8289.html#section-3.1)

## 6. 负载与对照应补哪些，何时做

9轮task异质性与9轮burst已分别由4008/4009完成，其后截至4016的审计、信号/线程、regular守护、S校准和SD六轮也已完成，见[最新结论](TARGET_V2_4016_REVIEW.md)。SD的request峰值在途数为3，不能据此认定持续饱和或启用时间门控。当前仅按[既有SD结果的到达核查指南](TARGET_V2_4016_NEXT.md)，用`arrival_audit.py`对已完成六个目录做只读、有界核查；无新增压力、trace或阈值试验。暂停扩大CPU工作族性能矩阵；后续工程优先实现等待期间释放executor worker、完成后重新提交恢复回调的异步工作族。v2驱动当前尚未实现该工作族，没有可执行的异步负载CLI。门控仍为后续独立候选；只有明确现有策略缺口与可路由机会时再选择专项工作族。本页不提供gate的ARM执行命令，因为gate尚未实现。

| 必测形态 | 要揭示的问题 | 当前驱动状态 |
|---|---|---|
| 短而陡，峰值超过2C | 危机旁路是否把可快速消化的尖峰也大量借出 | 可用宽度/固定工作量构造；不是按CPU时钟强行早停 |
| 中等峰值、较长任务，其他池空闲 | 等3ms是否损失本可获得的并行收益 | 可用已有宽度、工作量/异质性；一次性提交还要单列无后续动作机会 |
| 中等压力持续超过hold，之后仍有新ready任务 | 延迟确认能否减少不必要迁移而保留收益 | 链/多波可部分覆盖；独立控制ready分段时序尚需新驱动 |
| 快速退潮后短间隔再次突发 | EWMA尾巴、旧计时器、采样空洞和滞回是否误触发 | 请求burst可部分覆盖；不能拿batch-chunk当时间间隔 |
| 同NUMA各池同时忙 | 门控开启时是否真的有合适目标 | 已有竞争负载可研究，需同时核对实际到达 |
| callback多但同步阻塞、或异步等待后集中恢复 | 所选N是否误判CPU；恢复峰是否可处理 | 同步反例已有；v2非阻塞RPC仍待实现 |

每种形态内部固定工作和到达，只改策略；不同宽度/工作量不是同合同。对20/80/400扇出做尺度扫描不能自动宣称等需求。分段ready需用非阻塞完成源或明确的释放驱动，记录planned-ready/actual-ready，不能靠worker sleep凑持续时间。

对照也应拆开，不一次把阈值、计时、EWMA、home平手优先全部换掉：

1. 保留现有即时策略作为锚点（4006为busy-high1，不是1.5C）。另以相同信号、start/release和目标规则比较hold=0与候选hold，才能识别持续性本身；0/.5/1/3ms是有限敏感性点，不是预定最优。
2. 在一个选定hold上对比emergency关闭/开启，再看快速退出规则；记录duration/emergency各自的实际新任务路由数。避免大扇出全部绕过hold后误称门控已被验证。
3. 最后单独比较目标当前值排序与带即时保护的EWMA排序；先同NUMA，再跨NUMA。保留未参与调参的seed和工作形态。

验收同时看整request mean/p95/p99、CPU/request、拒绝/lag、迁移及原因、门控有效覆盖、检测后的剩余压力/可行动任务、观测成本。是否“触发但N≤C”只作辅助诊断，不作为优化目标。只有在反例和独立压力上稳定获益后，才考虑将候选提升为推荐策略或推进第五阶段库归属。
