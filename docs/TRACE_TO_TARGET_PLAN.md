# 从4005调度证据到目标cluster实验：补什么、暂不改什么

**当前状态：4007～4010的有界历史证据分析和4011观测扰动均已完成，见[最新结论](TARGET_V2_4010_4011_REVIEW.md)。下一步为[计数信号/线程对照](TARGET_V2_SIGNAL_THREAD_GUIDE.md)，下文保留历史设计，不自动重跑旧trace。**

## 1. 决策与固定主线

需要补充有明确用途的解析，并收紧后续测试策略；**目前没有证据要求重写负载模型**。4005是历史未绑CPU的四池轨迹，目标始终是所选范围内每个已核实硬件cluster一个Folly子池，由RequestExecutor隐藏分组并实施两层调度。当前选定六cluster，所以是六池；历史池数、每池unique峰值和16 QPS都不是目标配置约束。

[4005审阅](TRACE_4005_REVIEW.md)已支持短时服务集中、线程过配及指标口径需要分开；它没有request/operator边界、Folly Q/I/O或内存访问信息。继续解释同一份五事件trace，不能补出这些不存在的信息。

4006的24轮、4008的task异质性和4009的burst竞争均已完成；结果见[4009审阅](TARGET_V2_4009_REVIEW.md)。当前入口调整为[真实负载校准协议](WORKLOAD_FIDELITY_PROTOCOL.md)：只用离线旧trace做有界补证，未知量保持假设范围，随后继续有限机制对照，不等待生产接入。旧trace不应无限重扫，但即使模拟结果自洽，也不能跳过生产代表性校准。

## 2. 历史trace还值得解析什么

| 问题 | 追加方法 | 对目标实验的用途与边界 |
|---|---|---|
| CPU服务集中在多少时间内 | 已保存JSON的完整固定桶；最忙10%桶占总onCPU比例，连续高桶长度 | 判断是否保留集中/持续两类压力；不是request突发持续时间或算子CPU预算 |
| 各池的峰是否同时出现 | 对齐同一时间桶后求和、统计同时高服务的池数 | 区分孤立尖峰与共同竞争；不能把各池独立最大值相加 |
| 一池服务高时，其他池怎样 | 条件统计其他池onCPU是否低于自身均值，并同时保留observed demand | 描述历史服务是否错峰；低onCPU不等于idle，更不能据此证明目标cluster可借资源 |
| 等待、调度迁移是否解释目标策略差异 | 在目标cluster配置的少量诊断轮记录映射、用户态关联和调度事件 | 出现具体策略异常时再做；历史无绑定池的OS迁移不能代替目标L2选池迁移 |
| 算子时长、内部ready节奏、RPC与数据亲和 | 新的业务边界观测，见第5节 | 现有五种内核事件不能反推出这些量；不继续用更复杂统计代替缺失观测 |

新增 `scripts/analyze_sched_windows.py` 只读已有 `sched-text-v1` JSON，默认动态选取所有非`[unmapped]`池，没有四池或六池常量。不重扫trace、不访问/proc、不启动负载、不更改原始报告。终端报告包含：

- onCPU均值、p50/p90/p99/峰值及最忙10%完整桶的服务占比；这些p值是**时间桶的CPU服务分布**，不是任务时延。
- `onCPU > m × 本池完整桶均值` 的桶比例及连续桶段长度，默认m为2、4。阈值仅定义该份trace的描述性高服务，**不是运行时繁忙阈值**。
- 同时高服务池数直方图、各池同窗求和后的onCPU与observed demand均值/峰值。
- `P(目标池onCPU≤其自身均值 | 来源池onCPU高)`，附来源高桶样本数。相邻桶相关，不能把它作为独立伯努利试验或空闲概率；未使用硬件容量推算可借性。

连续高桶段有桶边界误差、阈值依赖及左右边界删失；跨过观察边界的段会单列数量。它描述观察窗内连续固定桶，不识别request，也不能断言这是完整的业务burst持续时间。末尾不足一个桶单独报告并排除；缺series、截断、存储丢更新、错轴或无效数值直接报错，绝不补成idle。`coverage=unknown`、等待删失与名称推断的池映射限制仍随报告保留，读取成功不代表原始采集完整。

下述两档已有窗口已在4007完成，结果见[最新审阅](TARGET_V2_4008_REVIEW.md#4-4007支持长短集中段并存不验证3ms门控)。保留原命令供复现，不需重复运行；没有新依赖，不需重编C++/Folly：

## 3. 当前模型能覆盖什么，实际缺口是什么

| 维度 | 当前实现 | 后续动作 |
|---|---|---|
| 请求与内部并发 | 开放到达regular/poisson/burst；每request多波分支链、join和初始大扇出 | 4009已完成新图burst；真实executor到达与内部ready形状仍须校准 |
| 成本异质性 | request或task级固定seed扰动、长尾倍率均已支持 | request/task机制对照已完成；需实测长算子与请求类型/关键路径的联合关系 |
| 线程过配与信号 | 固定worker数；Q、callback I、O、估计work及后台CPU可替换 | 保留16/128线程与Q/active/O少量对照；不能把窗口unique-onCPU当作I已获验证 |
| 数据亲和 | none/request-ro/branch-rw/mixed；home初始化、连续分支读写 | 先64KiB，再256KiB或共享读；不是对真实cache miss的复现或直接测量 |
| 内部ready释放节奏 | 一个callback连续addBatch，后继依赖自然释放，可配置后续wave | `batch-chunk`控制选池预留粒度，**不控制时间间隔**；非阻塞分段release需要新增驱动，目前未实现 |
| 异步RPC | 总池Continuation登记、恢复/取消与关闭测试已实现；v1有RPC实验 | v2固定工作/内存驱动没有异步RPC；需单独集成，不能拿同步sleep反例宣称覆盖 |
| 内存来源与计算形态 | home first-touch全部波的数组；每operator先计算循环再访存循环 | worker构图已触页、复用缓存、计算访存交织、大块多父融合尚未实现；结果或业务证据需要时再补 |

4004校准的普通后继CPU约4～6ms，不证明真实算子也如此。真实“平均100ms”仍需明确CPU或墙钟口径、算子个数分布和CPU/request。内核一次switch运行片段可能只是算子的一部分，也可能包含多个callback；禁止按它重新标定算子预算。

短算子可通过已有iterations/accesses参数试验；改变它会改变工作需求。若提高QPS补偿，又同时改变请求竞争。分别标记为“固定到达下减小工作”和“匹配平均需求的另一工作族”，在每族内部比较策略，不宣称纯粹隔离了调度粒度。trace0/1对照用于确认观测是否占主导。

## 4. 后续测试顺序与停止条件

4009后不自动继续参数扫描。具体步骤与验收见[真实校准协议](WORKLOAD_FIDELITY_PROTOCOL.md)：

1. 冻结已完成regular、request/task、burst机制结果；只读非生产分析机持有的旧trace及派生产物，不重复4007窗口统计，不访问真实业务或源码、不重采。
2. 缺少request/operator边界时，executor到达、CPU/request、图/ready、RPC和数据归属保持unknown，给出显式敏感性范围，不要求先完成生产抽样。
3. 据旧trace可观察现象或待检验假设，调整少量参数/模型能力，冻结输入与固定工作合同；内部ready依赖自然生成，不回放旧调度造成的等待。
4. 完成一次有界补证即可在独立ARM测试环境继续每cluster一池的信号/线程/容量等有限对照，用保留的合成形态检验稳健性，不将其叫真实留出验证。开发环境承担低资源功能验证，人工传递摘要即可。
5. v2异步完成源、分段ready或数据共享模型可按具体机制问题独立开发，不冒称已标定真实分布。仅在要确认生产收益/默认参数时，才提出所缺业务证据；该后置验收不阻塞当前研究。

若只能获得旧trace而始终缺request/operator边界，停止追求从同五事件还原业务模型，明确保留代表性缺口。可以继续机制研究，但不升级为生产收益结论；不以扩大合成样本量替代现场证据。

## 5. 后置参考：未来可接入真实业务时采什么

本节不在当前隔离环境执行，也不是后续模拟的前置条件。4009进一步表明负载形态影响策略收益。即使现有CSV中的机制可以解释，外推生产前也必须补真实业务特征；不能仅在出现异常时才观测。优先复用已有指标，缺失项用少量抽样补齐，内核trace仅在需要分解调度等待时采少数诊断轮。调度trace的记录开销不混入正式性能轮。新采集按[trace工作流](TRACE_WORKFLOW.md)保存时钟、过滤/CPU覆盖、丢事件与映射证据，不能只采目标CPU而遗漏外部唤醒方。

生产可复用的最小关联设计：

- 在线程注册/退出时保存TID→pool→真实cluster/NUMA及生存期；稳定进程标识，避免TID复用混淆。不把名称正则当注册证明。
- 抽样完整request，记录request/operator/parent标识、ready/提交/start/end、home/source/chosen、原因及带采样时刻的Q/I/O。各时刻的具体落点需定义清楚，不能把ready→submit的路由时间计入Folly队列；现有demo task submitted在选池之后。
- 请求级CPU总量、operator CPU/wall分布；CPU时钟可只对选中的完整request启用。RPC开始/完成/恢复和取消单列，区分外部等待、ready未提交、池内等待与运行。
- 用户态与内核时间轴必须建立可验证的对应。多个独立relaxed读是近似观测，不伪装成原子快照；配套runq只用于同窗诊断，不等同Folly Q。

这些是通用总池/业务边界契约，不要求生产图携带demo节点标签。实现上优先线程本地有界缓冲、批量异步导出、明确丢记录计数；热路径不扫/proc、不逐事件打印、不为统计新增全局日志锁。抽样和注册本身也有成本，必须测开关对照。现有v2完整trace是诊断实现，**尚未提供上述生产级抽样、时钟关联和导出适配器**，不能将这段设计当作已经接入生产。
