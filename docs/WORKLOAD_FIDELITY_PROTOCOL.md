# 真实负载校准：让机制实验获得可外推的边界

## 0. 当前隔离条件与可执行范围

用户已明确：真实应用、测试与开发环境无法直连，当前不能访问真实业务；旧trace已复制到另一个非生产环境，由那里的agent分析。**本阶段不要求真实应用访问、业务源码、在线指标、重新采集或生产插桩。** 第4～5节的业务观测和第7节的真实外部验证是以后具备条件时的方案，不是继续模拟/工程的前置条件。

当前采用“旧trace约束可观察现象＋未知业务量的显式假设范围＋目标cluster下的稳健性实验”。生产代表性无法完全验收，应保留结论边界；这不等于工程无法继续。若将来某项具体结论确实没有生产证据就不可辨识，应指出该结论与最小证据，不笼统要求开放真实环境。

## 1. 当前判断与优先级

**4010已完成一次有界离线补证，4011已完成观测扰动对照。** 结论见[最新审阅](TARGET_V2_4010_4011_REVIEW.md)：旧trace无法识别request/operator/RPC/数据变量，新增外部解析器还有状态/分桶缺陷。本阶段不要求继续重扫或生产采样，未知业务量保留为显式假设。

当前优先级：冻结已完成结果 → 在固定合成合同下做[有限信号/线程干预](TARGET_V2_SIGNAL_THREAD_GUIDE.md) → 按具体缺口选择稳健性工作族。现有模拟尚未验证生产代表性；这不阻塞独立工程。能够访问真实应用的当地agent使用[分阶段手册](PRODUCTION_AGENT_PLAYBOOK.md)或[纯prompt版](PRODUCTION_AGENT_PROMPTS_ONLY.md)，先核实本地事实，再在授权范围做业务关联验证。

目标保持每个选定硬件cluster一个池，当前六池。旧四池未绑CPU是观测来源，不能重分成六池充当目标验证，也不要求把四池重新部署起来。无法取得真实业务特征时保留未知；目标cluster的生产性能外推仍属后续待验收项。

## 2. 当前模拟哪些已成立，哪些尚未校准

| 维度 | 当前实现/证据 | 真实业务缺口及影响 |
|---|---|---|
| 拓扑与调度接口 | 六个核实cluster；128线程/池；RR request home；统一add/addBatch与后继上下文 | 能检验目标资源约束，不代表128线程或阈值是生产最优 |
| 初始大扇出与依赖 | 固定80/4宽、2/2深；168算子+init+两个join | 20～400是初始宽度还是总节点数仍未形成分布；真实多父依赖、深度和关键路径未校准 |
| 请求到达 | regular12QPS与burst8；4009实际批内attempt约0.694ms | **应用入口QPS不等于executor阶段的到达过程**；worker构图可重新聚集/打散请求；没有证据表明真实入口每约667ms聚集8请求 |
| 内部ready过程 | 首波80个add连续完成，后继依赖自然释放 | 真实首波是否分批产生、后续ready是否有重叠波/RPC回流尚缺；不能用入口burst替代请求内部突发 |
| 计算总量与粒度 | 固定计算/访问次数；当前算子callback CPU均值约8ms，整轮进程CPU/完成请求约1.36～1.38秒（含init、driver和观测等） | 与原描述“100ms算子”的CPU/墙钟边界尚未对齐；外部0.85ms线程周期也不能替代算子预算 |
| 长短相关性 | task/request作用域，±25%、约1/8为4倍 | 长算子是否聚集在同一分支/请求类型、与图宽/RPC相关，均未测得；独立随机扰动不能自动覆盖关键路径偏斜 |
| 数据亲和 | 每分支64KiB读写，home首次触页，后继真有数据依赖 | 实际worker构图触页、共享比例、重用距离、远端访问和多父大块融合未知；不能将64KiB称为生产工作集 |
| 外部等待 | 总池异步Continuation生命周期已有；v2驱动不生成异步RPC | 不能据纯CPU实验评价RPC恢复、阻塞回调或其对I/O计数的影响 |

当前request时延覆盖demo executor图阶段，不能直接与真实IO接入→worker构图→executor→响应的全应用端到端时延混称。数据来源相同、统计对象不同的“约30ms”“活跃80”也不是已匹配的模型特征。

## 3. 旧调度轨迹：下一次解析应回答的有限问题

先复用已有summary_exact JSON、派生区间及分析代码；只有缺少所需状态时才定向流式读取原trace一次。原始文件不传输、不整体装内存，保持真实历史映射。

| 定向问题 | 可取得的量 | 如何影响模型；不能怎样使用 |
|---|---|---|
| 活跃到底是什么 | 明确unique-onCPU、瞬时running、runnable+running、线程wake→sleep周期各自定义；匹配率、删失及未知状态 | 决定能否使用外部8900/s与N=7.8；不能将线程数/唤醒次数改名为Folly任务数 |
| 压力如何形成和消退 | 起点已知的活跃周期、CPU服务集中段、已持续时间对应的剩余持续时间；按当前值分档而非未来最终峰值 | 判断是否值得补短密集/持续多波负载及门控；历史未绑CPU的消化时间不能照搬到16逻辑CPU |
| 服务与等待如何分布 | 连续onCPU片段、wake→run、runnable切出→再运行分别的样本数/分位/CPU总量；未知和删失单列 | 检查demo是否只覆盖长callback；onCPU片段不是算子，线程活跃周期可能执行多个算子 |
| 各池何时同时承压 | 已有同时间桶的联合服务与observed demand；明确重用4007而非重复做一遍 | 已支持保留孤立集中与共同竞争两类场景；低onCPU不等于可借容量，未绑CPU不能确认目标NUMA内空闲 |

现有采集质量仍有限：coverage未知、TID→池是名称推断、部分等待未闭合。必须将可复算子集与全体区分，不能为得到完整N(t)而用0填未知状态。waking发生在唤醒方CPU；只保留目标池运行CPU可能漏掉外部唤醒，当前机器的tracefs设置也不能追认历史配置。[ftrace官方说明](https://docs.kernel.org/trace/ftrace.html)

**五类sched事件无法补出**：request/operator身份、DAG边、Folly入队/出队、何时业务依赖满足、一次唤醒消费几个callback、RPC身份或分支数据重用。非R切出不等于RPC，长运行片段不等于长算子。继续扩大同一份trace的统计不能解决这些不可辨识项。

可直接交给现场agent的有界任务见[负载校准提示词](WORKLOAD_CALIBRATION_PROMPT.md)；外部3ms结论的细节按[持续性审计](TRACE_DURATION_AUDIT_PROMPT.md)执行。二者内容重合时只产一份结果，不重复扫描。该分析不是策略验收，也不以凑出完整历史状态为停止条件。

## 4. 后置方案：未来确认生产代表性所需的业务数据

本节不在当前离线任务执行，不要求用户取得新材料。未来具备业务接入条件时，优先复用届时已有日志、监控和代码边界。新观测以少量完整request为抽样单元，保留失败、取消、超窗和丢记录，不只采最快或成功请求。至少分别覆盖普通请求与已知长尾类型；初次画像样本不能当正式p99验收。

| 层级 | 最小字段/摘要 | 解决的问题 |
|---|---|---|
| 进程/部署 | 版本、Folly队列配置、worker实际数量、TID生存期与池映射、allowed CPU/NUMA/cluster、采集时钟/窗口 | 消除资源与统计口径混用 |
| 全量请求入口轻量记录 | request ID/类型、应用接入、executor首次接纳/初始ready、阶段完成、状态；起止在途数 | 区分前端burst和executor burst；对齐12/16QPS、阶段时延和边界 |
| 抽样完整图 | request/operator/执行段ID、依赖关系或fork/join关联、root/continuation角色、ready、路由前submit、选池后交接、callback start/end、TID/home/chosen | 得到总节点、初始宽度、多波、提交等待及依赖释放；join可能多父，单parent字段不能伪装完整DAG |
| 抽样执行段CPU | 同TID内start/end的线程CPU时钟差，与单调墙钟并列 | CPU工作与抢占/阻塞分开；跨线程异步算子逐段求和，不直接相减两个TID的CPU时钟 |
| 异步关联 | RPC发起/完成、恢复ready、取消、对应request/operator执行段 | 区分外部等待和占worker等待；刻画集中恢复 |
| 数据关联 | 从代码/既有指标确认读写/共享归属、典型字节数、谁首次写入、后继实际消费哪些前驱数据 | 给工作集与first-touch模型以依据；sched轨迹不能估计这些量 |

线程CPU时钟统计调用线程已消耗的CPU时间，不提供DAG身份或单独的runq等待；CPU时间仍受频率、缓存与内存停顿影响，不是跨部署不变的“工作指令数”。[clock_gettime说明](https://man7.org/linux/man-pages/man3/clock_gettime.3.html) runq归因需要同TID时间轴配合调度数据；schedstat的运行/等待计数应做差分，不能把总等待当请求关键路径等待。[内核schedstat定义](https://docs.kernel.org/scheduler/sched-stats.html)

第一份特征卡只需打印：有效request数/类型/状态，executor到达间隔与1/5/10ms窗口计数，算子数与初始宽度，CPU/request及按算子类型的CPU/wall分位，初始ready批大小/跨度，RPC比例/时延，以及工作集/首次触页已知项。特别保留联合关系：图宽与CPU/request、长算子与关键路径、请求类型与RPC，不只输出一组互不相关的边缘直方图。

相对executor进入后的1/3/10/30ms已ready数量可以作**实际执行结果**的形状诊断，但同时受依赖完成和原策略影响。要报告ready→submit与submit→start，避免把发生器或路由延迟当业务需求。

## 5. 后置方案：若未来接入观测，如何控制扰动

这是一份生产接入契约，不依赖demo固定节点编号；可在统一任务封装与图/RPC边界接入。stock Folly的TaskObserver适合任务领取/处理边界，不能独自提供业务ready、DAG边和RPC；已有FollyActiveLoadProvider也不是完整业务画像器。

- 在request入口做一次确定性hash抽样，抽样标记随异步上下文传播；不对各子任务独立抽样后假称拿到了完整关键路径。全量request阶段时间戳成本另计。
- 初次可选1/16 request作低采样率试点；12QPS、5分钟期望约225个入样请求，实际完整数要打印。它仅用于发现量级和缺项，不承诺尾部精度。若每request为20～400个执行段，CPU时钟读数的期望速率约为`2×12×(20～400)/16 = 30～600次/s`，这是操作次数预算，不是已测耗时；记录总次数和最坏突发。
- 工作线程只写预分配、有界线程本地缓冲；TID在注册/TLS初始化时缓存；后台批量输出并记录溢出。不要逐事件打印、全局日志锁或逐任务扫描/proc。缓冲大小和单request上限明确配置；截断样本单列，不能悄悄丢掉最大图。
- 对Q/I/O只做已有线程安全计数的relaxed读取；允许近似不等于允许普通整数数据竞争。若要新增observer或维护I/O计数，其每任务RMW成本须单独测量，不能因只抽样导出就称维护成本也降为1/16。
- 初次测量做关闭/开启抽样的同流量交错对照，记录进程CPU/request、阶段时延、丢记录及导出CPU。先规定可接受的扰动预算，再决定采样比例；不承诺固定的纳秒成本或“必然低于1%”。
- 用户态与内核时钟要校验对应。内核trace只在少量诊断轮开启，性能排名轮与重采trace轮分开，不能把“tracing_on=0”直接当所有探针成本都已撤销。

当前仓库**尚无已接入真实业务的抽样/导出适配器**，也没有用户真实业务源码。当前不部署此适配器，也不要求回传源码或hook；未来只有具备实际接口时才准备具体补丁。v2的完整tasks.csv是模拟诊断，不替代生产数据。

## 6. 怎样把证据映射为模拟，并防止循环论证

下列业务字段有证据时用于校准；当前离线资料缺失时保持未知，以敏感性假设研究，不要求先访问真实应用。

1. **先校准输入边界。** 用executor首次进入的到达序列/类型混合，而非只匹配全应用QPS。按request ID保留图规模、各执行段固定工作、依赖和外部完成合同，策略改变不得重新抽取任务成本。
2. **先解释每request工作总量，再解释细粒度。** 同时约束CPU/request、节点数和CPU片段分布，不能只用全局50%CPU反推每算子。当前整轮进程CPU/完成请求约1.36～1.38秒只是合成负载事实，须与执行段CPU求和分别核对，不能混用口径；旧trace覆盖不确定，不能用24.646核当量除口述16QPS充当已核实的真实CPU/request。
3. **保持因果依赖。** 实际内部ready墙钟曲线包含原策略的执行与等待结果。不能将它全部固定回放，再宣称比较了新调度策略；应保留DAG边和工作，让新策略的完成自然触发后继。确属外部到达的事件才可作为独立输入，外部服务若受并发影响也须注明简化。RPC应按发起后的延迟/下游模型产生完成，不能冻结旧轨迹的绝对完成时刻；新策略改变发起时间，否则可能回复早于发起或写死旧等待。
4. **分别校准粒度、突发和数据。** 如果真实callback多为亚毫秒，就加入相应短任务族，固定计算/访存次数并测观测开销；不能拿wake周期0.85ms直接重写算子时长。若真实需要分段ready、RPC恢复或多父数据融合，再开发对应驱动。`batch-chunk`不是ready时间间隔，入口burst8也不是RPC恢复模型。
5. **保留少数有业务依据的族。** 至少按实测区分CPU密集大fork、持续链/多波、外部等待恢复及数据共享特点；是否全部需要由现场证据决定。不能随意扩大矩阵后挑出喜欢某策略的子集。

## 7. 未来生产代表性怎样验收（不阻塞当前机制研究）

没有单个相关系数能保证模拟真实。将数据分为用于校准的窗口/请求类型和留出的验证窗口；参数冻结后再查看验证结果。现有10秒trace不能拆出足够独立样本来宣称生产泛化。

验收分三层：

1. **输入与工作守恒。** 对齐executor到达率、类型混合、图规模/依赖、CPU/request及粒度、初始ready结构、RPC与数据归属。每项标“实测约束/敏感性假设/缺失”，保存来源、样本数和误差；同seed策略比较仍核对固定工作/到达/checksum。
2. **基线形状验证。** 在同资源、同口径的基线上，比较池间并发重叠、1/5/10ms服务/等待形状、长短压力比例、阶段时延及关键路径。不要求追踪每个内核switch相同；也不为匹配某个onCPU峰而破坏总工作/依赖。旧四池与目标六cluster不能逐池硬对齐，目标性能验证须用目标部署的新证据。
3. **干预与留出验证。** 先验证模拟是否复现真实部署中同工作、同资源的方向性变化，再评估home/fork/all及Q/active/O的收益。在真实参数不确定范围与保留工作族上若排名翻转，就输出适用范围，不发布单一最优策略。约1%的差异还需交错重复与更多请求，不能靠三seed各192个相关请求验收。

量化报告应打印CPU/request相对误差、图宽/节点/CPU段分布的分位偏差、到达聚集与压力重叠差异及丢失率。容差应在看候选策略收益前根据真实窗口间波动和计量误差确定，不能事后调宽直到通过；资料不足时明确“未完成代表性验收”，不杜撰固定通用通过线。

在这些证据补齐前，当前结论仍有价值：已验证总池实现、测量路径、首次分散收益，以及收益对请求竞争形态敏感。它们支持提出和淘汰机制假设；**不支持预计生产一定降低37%时延，也不支持把3ms或fork-only设为通用最优。**
