成功请求均值可以按`计划到达→完成 = attempt lag + attempt→完成`分解。排除已记录的直接lag分量后，Q相对home仍少46.279/45.652ms，O仍少47.108/46.162ms。因此几十ms的均值收益不能归因于这部分入口lag。

异常原因仍为unknown；这项分解不能排除系统共同干扰或到达变化的间接反馈。attempt在request构造/root add之前，不是root入队；各自的p99不能相减。当前不必为此强制重跑九轮或打开trace。若后续要解释异常，可对目标机已有两个home的requests.csv做一次只读摘要，列lag>1ms数量、top-lag请求的计划/实际attempt/完成及相邻到达间隔，无需新压力或新内核轨迹。

## 4. 对主线的指导与尚未回答的问题

本批与4012/4013共同支持：在已测CPU分支工作族中，cluster亲和home加同NUMA弹性借出有价值；worker预算应独立于池数调优，领取任务更快不等于request结束更快。Q有用且须保留，I/O可补充占用信息；这些量都不是内核runq。没有必要此时增加3ms持续性门控、改变高低阈值或修改Folly核心。

regular仍在每个request入口释放80个ready算子，平滑请求到达没有取消请求内部扇出。相对之前burst，它通常有更少的并发request及潜在空闲目标，这是更大收益的合理解释候选；本批trace0没有逐任务选池和各池占用，尚不能证实该机制。之前约7%与本次约38%的home收益来自不同时段，不能当作同期到达方式因果对照。

本批没有128线程，不能重新证明regular下16优于128；也没有真实异步等待、同步阻塞、持续饱和或跨NUMA借出，不能将16线程设为生产通用值。阶段3的条件负载/等待关联仍成立于对应合同；这里新增的是策略干预结果，没有得到统一的“负载→request p99”公式。后续应按工作族及容量分别验证，而不是将不同条件拟合成一个静态阈值。
