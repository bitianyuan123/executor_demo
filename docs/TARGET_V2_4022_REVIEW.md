# 4022 证据复核：撤回未经校准的负载替换建议

**本页修订撤回“先跑80×1+4×22、再完成三档矩阵”的下一步建议。** 4022足以证明原模型计算集中于宽波，不足以确定真实业务应当改成什么图。此前从“原模型代表性不足”跳到“这组新图应当必做”，缺少证据。`shape-coverage`仅保留为未校准的结构敏感性实验工具，不替换旧基线、不作为生产模型，也不作为当前必做覆盖。

当前顺序是：分析历史trace尚未解释的峰间背景和再次突发，同时离线恢复已经采集的demo CPU曲线；据此确定下一版模型的可测约束，再设计并验证图结构、阶段工作和请求相撞实验。此修订没有新增性能结果，不改变调度算法、阈值、C++负载默认值或每硬件cluster一池的目标。

## 1. 4022证明了什么，没有证明什么

两份成功输出来自旧4021的 `01-home` 和 `03-outstanding` CSV重分析，没有重新运行这两组240请求。下表使用全240请求，不与原192请求正式cohort混用。

| 指标 | home | O |
|---|---:|---:|
| 请求 planned mean ms | 120.275 | 73.119 |
| 每请求 timed callback CPU ms，均值 | 1367.560 | 1371.818 |
| 首波全部深度 / 全部业务算子 CPU 份额，逐请求均值 | 95.732% | 95.744% |
| 单请求 CPU / 请求过程时长，逐请求均值 | 11.434 CPU当量 | 19.172 CPU当量 |

显式诊断样本request6的home/O过程分别为127.341/74.004ms，CPU面积1374.030/1358.920ms；累计交付90% CPU的时间界分别为80.508–80.534/34.613–34.646ms。home仅CPU面积就需要 `1374.030/16≈85.877 ms` 的理想供给。**该3M模型不是只在开头1–2ms消耗服务的负载。** 这不证明整个过程连续满载，更不能由单个request6推断生产请求。

证据支持保留给定模型下的均衡机制结论，不能推出真实请求的首波比例、后期并行度、DAG或最优策略。源行号和计量边界见[4022证据](../results/review/4022_summary.json)。

## 2. 为什么撤回80×1+4×22作为下一步必做实验

旧图和新提案实际分别为：

```text
旧基线：init → 80条深度2的分支 → 整波join → 4条深度2的分支 → join
新提案：init → 80条深度1的分支 → 整波join → 4条深度22的分支 → join
```

两者都有168个业务算子、171个callback、84份64KiB分支数据。新提案把首波固定工作计数份额从160/168降到80/168，目的是提供等总工作计数的结构反例。**80、4、22不是由历史trace标定的图参数。** 等计数不是等CPU成本；47.62%也不是已测CPU份额，更不证明首波持续时间或峰后背景已经吻合。

源码复核发现的缺口比这一次参数修改更早：

| 问题 | 现有实现与限制 |
|---|---|
| 复杂依赖 | 两图都只有分支内串行和整波barrier。没有跨分支局部join、多父依赖、局部再扇出或不同阶段流水重叠 |
| 数据依赖 | 本分支后继复用本分支buffer；后波另用buffer，join读取结果摘要。尚未模拟多父数据融合与阶段间大块数据传递 |
| 变更同时影响多项因素 | 22段链改变关键路径、同buffer复用次数及路径hop预算作用，不能把收益差归为单独的“扇出缩短” |
| 头部是否仍过重 | 首波仍提供80条可并行分支；其CPU面积、服务时间及init成本未在目标机测量，不能凭算子比例判断 |
| 旧请求与新扇出的相撞 | regular 12QPS全局间隔83.333ms，六池RR的同home间隔500ms。是否发生同池/同NUMA竞争取决于生命周期、路由、等待与到达相位，不能靠拉长链宣称覆盖 |

现有`arrival_audit`统计请求生命周期，`flow_report`按算子角色汇总；它们没有联合回答“旧请求后期在何池持有多少ready/执行工作、新请求在何时向同一资源扇出、双方各损失多少”。以前的burst和高QPS实验有机制价值，也不能代替这项联合归因。旧模型并未实现任意复杂DAG，不能把新提案说成只是对一个已完备模型做微调。

## 3. 历史trace值得补哪些证据

已有同10秒窗口的S1/4007结果是：单池平均matched on-CPU为4.364–7.093当量，最大1ms桶为72.167–78.559；最忙10%的1ms桶承载45.532%–54.827%的CPU服务。由补集得到，其余90%桶仍承载**45.173%–54.468%**，不能忽略峰间活动。这个补集是全池服务分布，不是每请求后期工作比例。

高服务段采用“超过本池全窗平均值两倍”的描述阈值，时长p50约2ms、p95约15–20ms；不是统一的N>16过载，更不是请求或算子时长。尚缺峰前/峰后背景、段间距与再次突发、各池同窗背景的条件统计。**这些可以利用已有历史trace继续分析；缺少业务标记不等于旧trace已无分析价值。**

具体可直接复制给持有旧trace的agent的[定向提示词](TRACE_TEMPORAL_SHAPE_PROMPT.md)只要求旧trace或既有可信中间序列，不需要访问真实应用、业务代码或重新采集。优先复用S1完整1ms序列，不沿用4010审计发现缺陷的S3分桶结果；必须重读时只做一次有界流式处理。

需要区分可观测与不可辨识：可以测全池服务脉冲和持续背景；无法把某个峰认定为某请求入口，也无法把峰后工作分配到旧/新request。历史未绑CPU的四池只能提供采集条件下的约束，不能直接拟合成六个cluster池，或把原服务曲线截到16当作绑定后的需求回放。时钟、coverage仍unknown时应保留限制，零匹配服务不解释为真实idle。

## 4. 已有demo采集只需离线恢复

4022有四次采集进入离线分析后失败，没有产生新的可用细粒度曲线。首次3M明确报告 `line 1: malformed switch payload`；用户随后确认三种主要配置均为同一错误，并提供perf输出：

```text
[000] 128173.903316950: sched:sched_switch: perf:824058 [120] D ==> migration/0:17 [0]
```

原解析器只支持 `prev_comm=... prev_pid=...` 的具名字段格式，未支持这里的紧凑格式。已兼容两者，保留切换链、丢事件、时钟、TID与CPU归属检查；目标机仍须重新解析并通过这些完整性检查。当前报错发生在离线分析，不能据此认定负载运行失败，也不是已经得到375k形状的结论。

更新Python后执行以下命令，保留原目录，用新目录保存解析结果；不重编，不运行demo，不重采perf：

```bash
cd /home/bty/rank_demo/executor_demo
test "$(git branch --show-current)" = 'experiment/affinity-load-20261114'
git pull --ff-only origin experiment/affinity-load-20261114

for d in request-cpu-3m-home request-cpu-375k-home request-cpu-375k-outstanding; do
  python3 experiments/affinity/request_sched_profile.py \
    --run "results/local/$d/demo" \
    --trace "results/local/$d/sched.txt" \
    --capture "results/local/$d/capture.json" \
    --request 6 --bin-ms 1 \
    --output "results/local/$d/profile-format-v2" || break
done
```

成功输出包含 `payload_format_compact` 计数、摘要和窗口序列，可直接复制终端。原 `execution.json` 仍记录当时的失败，新的profile不改写历史失败记录。若再次报错，打印错误即可；不要为了换解析器重复压测。`request-cpu-3m-home1`是另一次独立采集，按需另行分析，不和首轮混合。

## 5. 下一版模型与实验的验收条件

目前不指定新的宽度、深度、工作档或持续时间。下一版设计必须分别注明用户提供的业务事实、trace支持的统计约束和无法识别的假设。不能为拟合一条CPU曲线只挑一组参数，再将其称为生产模型。

| 必须回答的问题 | 设计与后续验收要求 |
|---|---|
| 扇出是否短促，后期是否仍有显著工作 | 同时比较脉冲峰值、时长、CPU面积、峰间背景及再次突发；避免只拟合平均CPU或最大值。历史无请求标记时不要求逐请求直接配准 |
| 复杂依赖是否改变均衡效果 | 保留原图作机制基线；候选模型需支持局部fork/join、多父依赖及阶段重叠，明确数据消费和关键路径。具体实例与参数待证据约束后设计 |
| 新旧请求是否真实竞争 | 记录request阶段、ready/开始/结束、实际池；将旧请求后期占用与新请求首波按同一时间轴关联，分别评价新请求和旧请求完成时延，不能只看总在途或整轮p99 |
| 相撞是到达相位还是每请求工作改变造成 | 在固定每请求工作与依赖下，对照没有相撞、旧请求后期尚在服务时相撞、再次局部扇出；相位来自实测阶段窗口，单列有意构造的压力反例 |
| 对照能否归因 | 先固定策略验证负载形状，再在同合同内比home/Q/O；线程、NUMA、迁移继承规则和阈值分别研究，不与新图同时混改 |

“长期执行状态”可能包含CPU段、同步等待或释放worker的异步等待，三者不能靠给四条链增加CPU工作统一代替。缺少现场标记时，它们是明确标注的敏感性维度，不擅自指定占比。复杂依赖的生产实例仍不可由sched事件唯一恢复，但可以在得到时间形状约束后构造多个合理反例，检验结论是否依赖某一种拓扑。

现在只推进历史数据分析和已有demo采集的离线恢复；**不要求运行shape-coverage十二轮或三档矩阵**。该工具保留兼容性，输出明确标注“未校准假设、执行建议撤回”，今后若有明确结构敏感性问题再单独使用。算法、Q/I/O/R口径、原始实验合同和历史结果保持原样；持续压力门控与3ms等阈值没有因此得到验证。

此前[4022功能验证记录](../results/review/4022_validation.json)只证明工具能执行和工作计数守恒，不能验收负载代表性或复杂依赖覆盖。
