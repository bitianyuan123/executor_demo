# 4018：异步首批八轮完成，保留O候选并补齐恢复路径观测

**本批证明异步工程已能在目标六cluster资源上完成固定工作对照；在当前A1合同下，O相对home请求均值降低19.546%、p99降低20.752%，整轮CPU/请求增加3.721%。** 这是本批的时延与CPU权衡，不是生产最优配置或尾部验收。现有结果没有要求修改核心调度算法、默认阈值、完成源或CPU工作尺度。

下一步仅做[四轮A1机制覆盖](TARGET_V2_ASYNC_MECHANISM_GUIDE.md)：home/O各跑trace0与trace1，补齐O的源等待、恢复排队及观测敏感性。沿用每个已核实硬件cluster一池、透明总池、request home与新ready callback两层调度、仅同NUMA借出的主线；不回到历史四池配置，不重新获取生产trace。

每格1920请求全部完成，失败/拒绝0；按计划到达`[2,18)`选择的1536请求全部完成，迟到完成保留。固定工作签名前缀`223ea3119f9bbdce`、arrival hash `8354655555075271473`、checksum `12935529526370272479`一致；整轮迭代数166355865000、访问数5545195500相同。D0/A0/A1完整执行合同不同，不能因为业务工作相同就把结构差异称为纯策略成本。

O在三个合同里均表现为请求更快、整轮CPU/请求更高。不能将它写成“同时节省CPU”，也不能把本批没有运行的Q、work、其他线程数或跨NUMA策略排除。

A1中O的均值绝对收益为4.443ms，A0为6.092ms，说明收益缩小不仅来自百分比分母变大。但这不证明哪个内部环节退化，也不足以调整O阈值。固定外部等待会改变ready时刻、重叠及关键分支；O路径本轮只有trace0，没有迁移与恢复等待明细。

## 3. 异步结构与外部等待分别带来什么

| 干预 | home请求mean变化 | O请求mean变化 | home / O CPU每请求变化 |
|---|---:|---:|---:|
| A0−D0 | +0.346ms（+1.938%） | +0.182ms（+1.521%） | +2.267% / +0.707% |
| A1−A0 | +4.521ms（+24.831%） | +6.171ms（+50.935%） | −0.123% / −1.886% |

差值使用报告的原始比较列；由表中三位小数重新相减可能有0.001ms差异。这里不是对不同p99作可加分解。

A0增加了161076个控制callback，约为原callback总数的49.1%，仍维持相同业务工作。本批均值/CPU的增加较小，但home p99增加9.284%，不能把恢复结构概括为“零成本”。结构变化包含helper、登记/恢复、额外调度点和ready次序反馈，不能用CPU差除以恢复次数就当作一次add的精确成本。

A1的每个选中位置配置2ms，不代表每个请求只增加2ms，也不能用83.894个平均恢复次数乘2ms估计请求时延：分支等待可以并行，依赖链则会串行累积。A1−A0的CPU小幅下降也不能单独归因缓存、调度改善或更低能耗；本轮没有相应硬件与重复证据。

## 4. 已观测的home机制：请求变慢，ready排队反而变短

以下来自两格home trace1，均为完成请求cohort的事件/角色统计。

| 指标 | A0 | A1 |
|---|---:|---:|
| 请求mean / p99（ms） | 18.263 / 23.176 | 22.690 / 27.226 |

| 恢复控制callback CPU / wall均值（ms） | 0.002 / 0.003 | 0.002 / 0.003 |

A1的恢复排队均值比A0低约45.0%，业务operator等待低约10.8%，请求却更慢。这与外部等待重新分布ready工作相容，支持将外部pending、请求存活、CPU池Q/I/O分别计量。它不是完整关键路径证明，也不是“O通过减少这些等待获得收益”的证明，因为这里两格都是home。

O仍按callback计数，约2µs CPU的恢复控制与约1ms CPU的业务operator均占一个计数。成本异质性值得保留为观测维度，但本批O仍有收益，尚不能据此宣布count评分失效或直接改为CPU加权。现有Provider/Scorer接口及角色记录足以继续评估，不新增热路径原子计数、系统调用或定时采样。

source due→fire是模拟外部完成源的延迟，不能归入Folly任务队列或内核runq。恢复submitted在选池/预留之后，等待统计不覆盖完整路由成本；fire→submit单列了其中一段。callback可能重叠，分位数不能相加得到请求p99。

## 5. 完成源、入口与观测开关的限制

源pending峰值为65～94，最高仅占4096容量的2.30%，没有容量逼近或拒绝。helper CPU/请求为0.795～1.027ms，粗略折算为整轮约1.53～1.97秒CPU，约0.08～0.10个逻辑CPU时间当量。这个估计使用打印精度及约20秒墙钟；CPU窗口还包括origin之前的源创建/启动，不能当精确单线程利用率或硬件计算能力。

平均helper CPU低不排除短时串行派发、锁等待或被调度延迟；本批source lag p99约2.6ms、max约6ms，仍需保留。没有证据要求扩容源、增加helper或把AIO迁到额外CPU。整轮结束约20.003～20.017秒，仅比最后计划到达19.989583秒晚约13～28ms，未见长尾排空失控；这不是逐秒backlog或稳态认证。

home trace0入口lag均值D0/A0/A1为0.270/0.178/0.162ms，O约0.053～0.054ms。扣除入口lag的**均值**后，attempt→完成差仍存在；入口差不是全部请求差。这里不重新展开4017的相位根因调查，也不删除高lag样本。全局平均CPU时间约17～18个逻辑CPU当量，不能据此宣布全机容量极限，更不能从均值推断任一cluster的瞬时饱和时长。

## 6. 本轮工程决策与下一步

1. **更新结论和指南，保持C++工作模型与策略不变。** 无失败/守恒问题，无依据重新标定工作到0.85ms、启用3ms持续压力门控、改阈值、扩线程或改Folly核心。
2. **四轮补齐A1的O路径及两策略各自观测敏感性。** 使用同一seed/work和新目录，四格同期执行，避免拿4018历史trace0扣减新trace1；不重复D0/A0，不增加对齐网格、延迟或比例梯度。
3. 四轮只回答O的恢复/业务等待、源lag和路由角色变化，以及trace是否改变结果解释。它不能强制得到“O每类等待都下降”的结论，也不构成独立尾部重复验收。四轮完成即停止；若源或观测反馈明显，先限定模型适用范围，不通过改参数制造预期结果。
4. 真实环境可以参考“外部等待释放worker、恢复保留home/parent上下文、源与CPU队列分开计量、同NUMA借出保留回退”的工程结构。实际RPC运行时与线程预算仍由当地agent核实；不直接复制16线程、96QPS、50%、2ms或当前阈值。
