## 2. home的lag有明显序号规律，但尚无CPU归因

以下为cohort的入口lag。1ms仅用于描述性分层，不是调度繁忙阈值。

| 每池线程 / 策略 | lag mean / p99 / max（ms） | lag>1ms请求 | 其中ID%6=1 |
|---|---:|---:|---:|
| 16 / home | 0.302 / 3.312 / 3.890 | 173/1536，11.263% | 171/173，98.84% |
| 128 / home | 0.275 / 3.083 / 4.578 | 153/1536，9.961% | 150/153，98.04% |
| 16 / Q | 0.055 / 0.059 / 0.089 | 0/1536 | 不适用 |
| 16 / O | 0.055 / 0.061 / 0.072 | 0/1536 | 不适用 |
| 128 / Q | 0.055 / 0.059 / 0.065 | 0/1536 | 不适用 |
| 128 / O | 0.055 / 0.059 / 0.061 | 0/1536 | 不适用 |

home的高lag并非均匀散落，确实与请求序号相位有关。但序号余数不是实测home、执行池或CPU：不能由`ID%6=1`宣称cluster 1、第二个池或某个CPU有问题。

源码中`submitted_ns`在当前request构造/root add之前记录，lag是计划到达至该driver时刻的延后。它不能归因于尚未开始的当前request执行池。此前请求的driver工作、共享CPU并集上的其他线程、timer/wakeup和调度等仍是未区分的可能因素；现有终端证据不足以确认任何一种。也不能把约3ms的尾部直接映射为历史建议的3ms持续压力门控。

home的六条top样本中，前一次至本次attempt间隔为13.950～14.941ms，随后一次间隔缩短为5.892～6.882ms；regular计划间隔约10.417ms。这展示了延后之后下一次发起间隔缩短的现象，因此计划相同并不保证实际到达间隔相同。无需继续按更多余数或相邻池猜测去挖掘本批数据；已知限制随结果一起保留。

home高/低lag组的attempt→完成均值只差0.038ms与0.133ms；分组后的主要可见时延差在入口lag这一段。这是描述性的条件分组，不是随机化对照，不能证明lag没有间接改变请求重叠、资源竞争或相位选择，也不能删除高lag样本后输出“修正后的策略收益”。两个p99不能相减。

## 4. 请求重叠量化了；它不是池负载或获益机制证明

以下从所有请求区间裁剪到墙钟`[2,18)`后按时间加权，包含窗口前到达但仍未结束的请求。它与按计划到达选出的1536请求cohort是不同统计总体。

| 每池线程 / 策略 | scheduled→终态平均重叠 / 峰值 | attempt→终态平均重叠 / 峰值 | attempt区间重叠≥2的时间比例 |
|---|---:|---:|---:|
| 16 / home | 1.721 / 3 | 1.692 / 3 | 68.882% |
| 128 / home | 1.736 / 3 | 1.709 / 3 | 70.490% |
| 16 / Q | 1.129 / 2 | 1.124 / 2 | 13.635% |
| 16 / O | 1.147 / 2 | 1.141 / 2 | 15.095% |

每轮均有1537个与墙钟窗口相交的区间，cohort仍是1536个请求。这不是多发或重复计数。scheduled区间包含入口lag，attempt区间还包含request构造；它们均不是Folly队列Q、callback执行中I、未完成ready任务O、内核runq或单池竞争数。

4016的整轮`peak_inflight=3`与本次Q/O的窗口attempt峰值2不冲突：前者是整轮RequestState生命周期统计，后者是固定墙钟窗口内attempt至终态的区间重建，窗口与生命周期口径都不同。128/O的scheduled峰值3、attempt峰值2同样体现区间起点的差别，不能强行改成一个共同峰值。

Q/O的重叠时间较少，与相同计划到达率下更短的请求响应相容；响应变短本身就会缩短重叠时间。因此不能用这组重叠结果反向证明“竞争消失导致性能提高”，更不能证明所有池不忙或同池完全没有竞争。trace0没有提供任务位置与池内时序，缺失保持缺失。

## 5. 对工程与后续实验的约束

本次完成到达异常的有界审查，不调整短工作负载参数，不重跑home/Q/O×线程矩阵，不新增trace或门控阈值。没有得到改变生产CPU亲和配置、选定Q/O赢家或直接部署某个静态阈值的依据。

CPU主导工作族暂时冻结，保留当前结果及其限制。需要推进的结构缺口是[真正异步等待与恢复](ASYNC_CONTINUATION_WORKLOAD_DESIGN.md)：算子发起外部操作后释放worker，外部完成使恢复callback进入ready调度，request上下文与续执行位置规则得以保留，取消和排空可以验收。该工程的完成状态由对应实现与测试记录确认，本证据报告不提前声称实现完成。

后续功能验收通过后，才建立直接执行、零延迟外部恢复、非零延迟外部恢复的对照，分别核对相同CPU工作与恢复callback开销。同步sleep只能作为阻塞反例，不能代表RPC；增加请求端到端时长也不等于增加executor繁忙程度。外部等待期间不应把未ready的未来算子当作已接收ready任务O来评分。

这些工作无需连接生产环境、重新采集生产trace或获得生产代码，且不依赖历史四池配置。当前尚无负载到request p99的通用公式，合成结果应作为当地功能核查与调优候选的依据，不能替代真实应用中的分阶段验证。
