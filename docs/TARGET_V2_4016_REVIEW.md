六轮SD完整，已观察到请求重叠。**Q/O相对同期home的请求均值下降约33%～34%，整轮CPU/请求增加约6%～7%。** 这支持在当前工作族保留同NUMA借出，同时明确短工作下的CPU代价；不足以选定Q/O赢家或生产线程数。本批结束，不继续加QPS或扫描阈值。

## 2. 明确记录时延与CPU的权衡

以下请求时延属于1536请求cohort，CPU/请求属于整轮1920成功请求，单位ms。

| 每池线程 / 策略 | request mean | request p95 | request p99 | 整轮CPU/请求 |
|---|---:|---:|---:|---:|
| 16 / home | 17.923 | 20.656 | 22.028 | 176.967 |
| 16 / Q | 11.757 | 14.615 | 15.760 | 187.598 |
| 16 / O | 11.943 | 14.953 | 16.023 | 189.416 |
| 128 / home | 18.077 | 20.898 | 22.377 | 176.889 |
| 128 / Q | 12.009 | 14.996 | 16.166 | 188.000 |
| 128 / O | 11.970 | 14.982 | 15.844 | 189.220 |

同线程相对home，Q均值下降34.40%/33.57%，CPU/请求增加6.01%/6.28%；O均值下降33.36%/33.78%，CPU/请求增加7.03%/6.97%（顺序16/128）。每请求多消耗约10.6～12.4ms进程CPU，不能把它隐藏在仅报告时延改善的结论中，也不能将两类指标直接相减成一个未定义的净收益。

这是配置干预后的整个执行CPU差，包含评分、预留/计数、唤醒、执行位置/数据访问变化及调度反馈等可能成分。trace0无法分解这些来源，不能直接称为cache miss、迁移或读取Q/O的成本；历史home trace成本也不能用来扣除本批路由成本。较长CPU工作族下的低比例不保证短工作仍有相同比例。

16线程下O均值比Q高1.58%、CPU高约0.97%；128线程下O均值比Q低0.32%、CPU高约0.65%。排名随线程档改变，保留两种实现，不据单次微小差异选赢家。16相对128的均值差分别为home约−0.85%、Q约−2.10%、O约−0.23%，O的样本p99反而较高约1.13%；仍不能推导全局最优线程数。

样本p99相对home均下降约27%～29%，但1536请求的名义尾端约15个请求仍不是独立整轮重复。请求/算子依赖、时间相关及顺序差异没有被消除，本批不构成生产尾部保证或小效应置信区间。

## 3. 请求重叠已覆盖，持续饱和没有得到证明

六轮peak均3，完成了4015孤立请求校准之后的重叠覆盖。每秒计划到达和attempt均96；home的一秒边界request backlog始终1，Q/O为0或1，没有观察到边界积压持续增长。

部分Q/O桶有95或97次完成，这是跨桶完成流，不是缺请求。16Q、16O和128Q在墙钟`[2,18)`内完成1537个请求，由进入backlog为1、退出为0解释；正式计划到达cohort仍是1536，不能混合两个总体。

这些证据只支持有限request重叠，不能证明同池持续竞争、所有目标池都忙或持续饱和；一秒边界统计也可能漏掉桶内短时峰值。最终排空是有限运行结束条件，不是稳态认证。保持SD结果，不为了“证明足够忙”继续提高QPS。

## 4. home投递lag重复出现，但不是约6ms收益的直接主体

以下均为同一计划到达cohort，单位ms；两个p99不能相减来分解延迟。

| 每池线程 / 策略 | lag mean / p99 | attempt→finish mean |
|---|---:|---:|
| 16 / home | 0.302 / 3.312 | 17.622 |
| 16 / Q | 0.055 / 0.059 | 11.703 |
| 16 / O | 0.055 / 0.061 | 11.888 |
| 128 / home | 0.275 / 3.083 | 17.802 |
| 128 / Q | 0.055 / 0.059 | 11.954 |
| 128 / O | 0.055 / 0.059 | 11.915 |

成功请求均值可按`计划到达→完成 = lag + attempt→完成`分解。home与候选的直接lag均值差约0.22～0.247ms，占约6ms均值差的3.6%～4.1%；attempt之后仍相差约5.73～5.92ms。因此已记录的直接lag不能解释大部分均值收益，但不能由此排除实际到达变化的间接竞争影响，不能删除高lag请求后重新宣传“修正收益”。

home的16个一秒桶全部出现约3ms的lag尾部：16线程桶内p99为2.888～3.890ms，128线程为2.584～4.578ms。它不是仅启动时一个异常点。整轮与cohort的lag p99不同，应分开保留；当前也不能仅凭数值接近3ms，把它与历史建议的3ms门控关联。

源码可确认[driver与worker使用同一CPU并集](../experiments/affinity/main.cpp)，`submitted_ns`在`sleep_until`之后、当前request构造/root add之前。lag可能包含计时唤醒、运行调度、上一请求的driver工作或其他因素；既有CSV没有对应内核/driver分段证据，原因保持unknown。两home恰好先跑也限制了策略归因。实际业务中IO/worker/executor的资源关系还需当地核实，不能把本合成器投递反馈直接迁移为生产结论。

## 5. 下一步止于一次离线核查，随后转结构性缺口

新增通用离线工具`arrival_audit.py`复用既有原始数据审计，读取六轮已有CSV，无新采样或热路径成本。它分别输出：lag阈值及request ID余数相位、少量异常请求与全run相邻attempt间隔、lag分层的描述性时延，以及裁剪到窗口的scheduled→终态和attempt→终态时间加权重叠。相位不是实测home/CPU，重建请求占用不是callback占用或内核runq。

按[下一步指南](TARGET_V2_4016_NEXT.md)执行一次，保留全部请求及失败记录。即使发现相位集中，也只形成后续假设，不由现有CSV指定内核根因、修改亲和或强行重采生产trace。这项核查用于明确当前结果的适用范围，不自动触发重跑六轮、trace1或阈值扫描。

CPU主导工作族已有长/短工作、突发/regular、观测开关、线程和计数信号的探索。可以冻结：同NUMA借出有时延价值，代价随工作族变化，线程预算必须单独验证，Q有用且Q/O尚无通用赢家。当前仍未得到负载到request p99的统一公式，也没有支持持续性门控的新证据。

下一工程优先项是[真正异步等待与恢复](ASYNC_CONTINUATION_WORKLOAD_DESIGN.md)的最小实现和功能验收：worker释放、外部完成、恢复ready、取消和排空。现有设计与Continuation单测不等于v2驱动已经覆盖；本次没有新增该CLI。同步sleep可另作反例，不能替代RPC；跨NUMA和数据共享仍按独立合同研究。离线到达诊断不能成为无限延后这些已知业务结构的理由。
