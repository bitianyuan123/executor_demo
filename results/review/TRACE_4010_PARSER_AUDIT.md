# 4010外部调度解析器审计：候选线程周期，不是已标定任务需求

审计输入为回传`4010.log`，SHA256：`107e1de3cf26b4007b6e32529140dec2d207fcf3d52410c2e6cb661a9bf08984`。附件包含`bounded_gap_scan.py`源码、REPORT、`scan_gaps.json`和相同结果的stdout；JSON与stdout不是两次独立验证。下文行号均指完整附件`4010.log`，不是仓库源码。

本次只读审阅源码与汇总，并对摘出的外部解析器运行了下述2～4事件合成反例。没有读取或重新扫描约1GB的原始trace，没有将外部解析器纳入本仓库维护，也没有修改S1（此前仓库分析器）的统计规则。

## 1. 可采用的结论与需要降级的结果

可以继续采用的证据边界是：历史采集仍为四个未绑CPU的临时池，TID身份是名称推断，coverage仍unknown；没有request/operator/RPC标记，不能从这些sched事件恢复业务到达、算子CPU、DAG、RPC比例或数据亲和。外部agent报告没有找到最初1266个过载事件及EWMA重放产物，因此3ms/0.9C/0.75C/2C仍未获得验证。

S3新增结果可以记录为**该脚本、该状态处理规则下的线程周期候选统计**。它把wakeup到首个非R切出的区间作为一个周期，不能视作Folly任务；一个周期可包含多个callback，一次callback也可能因阻塞跨越多个周期。pool_a的闭合周期均值约868µs与外部约0.85～0.88ms相近，但不能反过来证明原N和8900/s采用了这个定义。

S3的瞬时N、等待积分、1ms桶分布不能升级为已验证的完整状态重建。下面证明了跨桶处理和异常状态维护的具体缺陷；其对真实文件的影响大小仍未知。尤其不得因它与S1部分running均值或最大值接近，就认可其所有等待、周期和桶结果。**本审计不推翻S1既有匹配区间、删失审计和4007摘要。**

## 3. 已复现的状态与分桶缺陷

反例只验证解析器在相应输入下的行为，不声称原trace一定包含同类缺失或乱序。运行时只将外部源码的TRACE/OUT改到临时文件，其余解析逻辑保持原样；跨桶例仅调用原`advance()`。

### 3.1 跨桶区间没有延续到后续桶

`advance()`（第85～106行）对完整`dt`累计积分，却只修改`last_ts`所属的一个桶：第95行计算桶号后没有循环覆盖相交桶。

最小复现：令池a已知running=1，从WS持续到WS+2500µs，调用一次`advance(WS+2500)`。原函数得到：

- running积分为2500线程·µs，正确；
- 前三个1ms桶的running最大值为`[1, 0, 0]`；
- 这段已知运行区间实际与三个桶都有正长度交集，正确最大值应为`[1, 1, 1]`。

因此桶均值/分位、`>16`桶数等不能直接称为完整分桶结果。真实trace事件密度很高，错误可能只涉及短边界片段；但脚本没有输出跨边界区间审计，无法由现有JSON量化影响。全局最大值碰巧与另一工具一致，不能验证所有桶分布。

### 3.2 已runnable的线程再次R切出会重复计数

switch-out处理第135～148行：如果线程并非已知running，只增加`switch_out_not_running`，仍继续处理；遇到R则无条件设置`runnable=True`并将池`wait_cnt`加一，没有检查该线程原本是否已计入。

使用同一TID，事件相对WS为：

| 时间 µs | 事件 |
|---:|---|
| 100 | wakeup，进入runnable |
| 200 | R切出，缺少此前switch-in |
| 300 | switch-in |
| 400 | S切出，线程进入睡眠 |

原脚本只报告一次`switch_out_not_running`，但等待计数经历`1→2→1→1`。线程在400µs已睡眠，残余等待计数仍持续到10秒窗口末，得到整窗`timeweighted_runnable_wait_cores=1.0`。缺少switch-in时应标记该周期存在歧义或重新建立状态，不能保留一个不存在的第二份runnable计数。

真实JSON确有a/b/c/d分别5/2/1/1次`switch_out_not_running`，但没有记录这些事件发生前的runnable状态，不能断言上述计数泄漏就在真实数据中发生，更不能按这9次直接估算误差。

### 3.3 非R切出没有清除原有等待计数

第145行先把`s["runnable"]`设为False，随后第146行又检查这个已经清零的字段，且分支体只是`pass`。因此线程在先前被计为等待、却缺少switch-in的情况下，非R切出不会减掉`wait_cnt`。

更短反例：100µs wakeup，200µs直接S切出（缺switch-in）。脚本关闭一个CPU=0、跨度100µs的周期，却让等待计数留到窗口末；真实累计等待为脚本的9,999,900线程·µs，打印四位小数后仍为`1.0`核当量。真实JSON的闭合零CPU周期为0，所以这个特定短路径没有被真实输出直接证明；它仍说明异常路径处理不完备。

### 3.4 乱序被静默接受，可得到CPU大于墙钟的周期

第88～89行在`ts<=last_ts`时直接返回，但调用者仍使用旧时间戳修改线程状态，没有乱序计数、拒绝或失效处理。

按文件顺序输入：300µs wakeup、200µs switch-in、400µs S切出。脚本输出一个墙钟100µs、CPU200µs、CPU/墙钟=2.0的闭合周期，`counts`为空。这个反例证明当前脚本不能自行验证全局顺序。

此前独立报告声称原文件无全局/逐CPU乱序，本次反例不否定该历史检查，也不声称真实结果存在比值>1。这里的必要限制是：不能将S3自身未报告乱序解释为已检查且为零。

### 3.5 初始unknown没有被单独表示

`get_st()`（第55～63行）将新TID的running/runnable均初始化为False，全局计数从0开始；没有已知/未知覆盖字段。只输入400µs的第一次S切出时，脚本报告`switch_out_not_running=1`、running积分0，却不能判断这个线程在窗口起点到400µs究竟运行了多久。

因此REPORT第288行“未知区间不补零”不准确：程序没有可表达unknown的状态，完整窗口归一化中未知贡献按零计入已观察计数。可以将其称为在这些初始化/延续规则下的观测估计，不能称完整线程N(t)，更不能把零桶解释成真实空闲。

## 4. 删失、对照与Little推论的其余限制

1. S3遇到重复wakeup或wake-while-running时只计数并保留现有周期；S1会对部分歧义/覆盖情况采取失效或删失处理，两者并非同一估计量。S3的周期右删失为19/1/6/2，而5259/3248/4977/5033是重复wake事件，不是同样数量的已剔除完整周期。REPORT第307行笼统“闭合样本删失约8～11%”没有相应S3分母，不能沿用S1的wake→run保留率解释S3周期分布。
2. REPORT第268行把S3与S1 running差异全部归于窗口边缘，缺少逐区间对齐支持。按此前已公布的四舍五入数，S3 waiting核当量0.633/0.374/0.584/0.584，比S1 observed-demand减onCPU得到的约0.361/0.208/0.336/0.335明显更高。删失、迁移覆盖及歧义规则不同均可能参与；不能因running接近，就声称等待也经独立校验。
3. 对pool_a，`8885.8/s × 868.094µs = 7.713711`仅是闭合周期面积除以10秒；与S3含其他边界贡献的run+wait=7.7693口径不同。这种近似相符支持一个候选解释，不证明外部最初的N=7.8和λ=8900就是此定义。REPORT第318行“证明原Little商是线程wake→sleep周期”应改成“存在接近的线程周期候选，但原定义未确认”。
4. pool_a逐周期CPU/墙钟比的算术均值为0.874，而CPU均值/墙钟均值为`797.103/868.094≈0.9182`。这不是计算矛盾，而是加权不同；不能用0.874乘平均周期时长推导平均CPU需求。
5. 此脚本没有输出连续过载段、landmark剩余时间或在线门控重放，更没有request标记。不能据其桶最大值或周期分布恢复1266事件、验证“92%自愈”、决定3ms门槛或证明迁移收益。历史池也没有16CPU硬上限，不能将`run+wait>16`解释成绑定cluster后的过载事实。
6. hook时钟读数“数十ns”等文字是未在目标环境验证的成本估计，不是本次trace测量结果。需要继续区分wall clock、thread CPU clock、记录和导出的成本；任何低扰动声明最终仍需独立开关或采样率对照。

## 5. 下一步：停止为这些旧数字反复扫trace

本轮不要求重扫原文件或重新采集生产调度轨迹。分母可以直接修正，缺陷已由小反例说明；即使把外部parser修到完整，它仍无法从无业务标记的旧文件恢复request/operator/RPC/数据画像，不能消除当前模拟真实性的主要缺口。

保留S1/4007作为有明确删失与统计定义的历史参照，S3新增量标为候选且附上述限制。不将旧四池强行拟合为目标六cluster，也不据候选868µs重写demo算子预算。进一步工程优先级仍是目标cluster实验的观测扰动与信号反例、以及条件具备时的最小业务关联证据。

如果未来确实需要将线程状态周期用于一个具体决策，应先明确为什么会影响决策，再在修正的解析器上补齐区间分桶、已知状态/删失、计数守恒与乱序检查，用小型合成轨迹验收后安排一次有界重算；不为追求“两个工具数值相等”而反复扫描或修改删失口径。
